# 执行追踪与结果交付 — 需求规格

## 概述

Agent 上报执行进度，平台检测超时并处理，Agent 提交 1~3 个候选结果，发布者选择结果验收或要求返工。对应 PRD FR-E01、FR-E02。

> 2026-08-22 体验映射：体验页验收只用于解锁下一步，刷新后丢失，不创建
> `task_results` 或结算状态。`RequirementsArtifact`、`DesignArtifact` 和 `CodeArtifact`
> 的版本契约集中在 `docs/workflow-artifacts.md`；本 feature 后续负责持久化其版本和验收。

- 架构类型: 多服务架构

## 用户故事

- 作为 Agent，我想要上报开始执行、进度、需要补充信息、执行失败或结果提交，以便发布者了解任务实际进展。
- 作为发布者，我想要查看最近状态、更新时间和预计完成时间，并在结果提交后选择一个结果验收，以便完成交付闭环。
- 作为平台，我想要重复或乱序的状态上报不会导致状态倒退，超时未交付的任务能自动进入已超时并停止无意义的重试。

## 功能需求

1. [F-001] 执行状态上报：Agent 可上报「开始执行」「进度」「需要补充信息」「执行失败」「结果提交」。
2. [F-002] 状态可见：发布者可查看最近状态、更新时间和预计完成时间。
3. [F-003] 防倒退：重复或乱序的状态上报不得导致任务状态倒退（如「已提交结果」之后收到「开始执行」不应覆盖当前状态）。
4. [F-004] `[v3 修改]` 超时处理：超过截止时间仍未交付的任务进入「已超时」，停止自动重试，进入人工处理或退款流程。**检测范围覆盖「待匹配」「待接单」「执行中」三个状态**，不只是「执行中」——如果发布者设置的截止时间偏短，任务完全可能在还没轮到执行、还卡在匹配或等待 Agent 接单的阶段 deadline 就已经过了，这种情况必须同样被检测到并转入「已超时」，不能让任务停在中间状态没人处理（资金也跟着卡住，见 [[4.task-creation-and-preview]] F-002 关于最短执行周期的讨论）。「待托管」状态不纳入此检测范围——那个阶段任务尚未被资金托管确认，属于 [[6.escrow-sync-and-wallet]] 的交易确认/失败恢复范畴，是另一套不同的失败处理逻辑，不应该用同一个 deadline 检测器覆盖。
5. [F-005] 结果提交：Agent 每次任务可提交 1~3 个候选结果，每个结果包含摘要、正文或文件引用、生成时间和必要说明。
6. [F-006] 结果校验：不符合数量、格式或安全要求的结果不得进入「待验收」状态。
7. [F-007] 版本管理：重复提交保留版本记录，并明确标识最新版本。
8. [F-008] 验收：发布者选择一个结果验收；验收前展示结算金额和手续费。
9. [F-009] 返工：支持要求返工，不默认无限返工；具体返工次数、时限、额外费用规则待确认。

## 非功能需求

- 一致性: 状态上报的乱序保护基于单调递增的状态版本号（复用 [[10.notification-and-sync]] 的 `task_events` 机制），不依赖到达顺序。
- 安全: 结果中的文件引用需要类型与大小校验，防止恶意文件进入交付物。

## 验收标准

- [x] [AC-001] 乱序到达的旧状态上报不会覆盖已存在的更新状态。
- [x] [AC-002] `[v3 修改]` 任务超过截止时间时，无论当前处于「待匹配」「待接单」还是「执行中」，都自动流转为「已超时」，且不再触发新的重试；「待托管」状态的任务不受此检测影响。
- [x] [AC-003] 提交超过 3 个结果或数量为 0 的请求被拒绝。
- [x] [AC-004] 重复提交结果保留历史版本，界面明确标识最新版本。
- [x] [AC-005] 发布者验收前能看到本次验收对应的结算金额与手续费明细。
- [x] [AC-006] 返工请求次数超过配置上限时被拒绝，并提示已达上限。

## 依赖

- [[1.agent-protocol-contract]]：结果提交与状态上报复用签名和幂等规范。
- [[9.dispatch-and-acceptance]]：任务已进入「执行中」状态（已接单）。
- [[10.notification-and-sync]]：复用其事件日志与状态版本机制。
- `[v3 新增]` `[[4.task-creation-and-preview]]`：超时扫描直接读取该 feature 定义的 `tasks` 表和 `TransitionTaskStatus()`，不需要依赖 [[8.matching-and-candidates]]、[[9.dispatch-and-acceptance]] 的具体实现——「待匹配」「待接单」只是共享状态机里的状态名，本 feature 的超时扫描是这两个状态的唯一 deadline 检测方，8、9 不需要（也不应该）各自再实现一遍。

- ~~平台手续费费率未定~~ `[v2 已确认]`：费率 0.4%，验收前的手续费展示调用 [[4.task-creation-and-preview]] 的 `CalculatePlatformFee()`（同一函数，见该 feature design.md 模块 5），不需要本 feature 单独实现或维护费率数值。
