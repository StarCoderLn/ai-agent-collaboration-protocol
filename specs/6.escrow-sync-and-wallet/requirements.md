# 链上事件同步与钱包交互 — 需求规格

## 概述

监听 [[5.escrow-contract-ethereum]] 的链上事件、确认后驱动任务状态迁移、与链上状态对账，并提供前端钱包交互（MetaMask）与交易状态展示。对应 PRD FR-T03 的链下部分与 PRD §11 P3 的 BE-E、FE-E。

## 项目信息

- 项目名: ai-agent-collaboration-protocol
- 架构类型: 多服务架构

## 用户故事

- 作为发布者，我想在所有阶段选定 Agent 并看到准确总价后再完成 MetaMask 托管，并清楚看到交易状态，以便知道已选工作流何时开始执行。
- 作为平台，我想要仅在链上交易达到规定确认数后才推进任务状态，以便避免因链重组导致的资金状态错误。
- 作为运营，我想要链下任务记录与链上交易哈希可核对，且失败的退款不会被误标记为「已退款」，以便安全地处理异常。

## 功能需求

1. [F-001] `[v7 修改]` 链上事件监听：监听 `Deposited`、`Released`、`MilestoneReleased`、`Finalized`、`Refunded`，写入链下事件与累计释放账本。
2. [F-002] `[v9 修改]` 确认与状态迁移：达到规定确认数后，`Deposited` 事件驱动任务从 `awaiting_escrow` 迁移到 `matching`、workflow run 从 `planning` 进入 `running`；根节点进入 `matching`，有未满足依赖的节点进入 `blocked`。重复回调或未达确认数不得推进状态。
3. [F-003] 幂等处理：同一笔链上交易（`txHash` + `logIndex`）不得被重复处理为重复入账或重复触发状态迁移。
4. [F-004] `[v7 修改]` 对账：定时比对链下记录与 `escrowOf` 的原托管额、累计释放额和终态，发现不一致时冻结相关操作并告警，不自动覆盖已有争议记录。
5. [F-005] 失败恢复入口：链上失败、金额不足、币种不符、交易超时的任务提供明确状态展示与人工/自动重试入口。
6. [F-006] `[v8 修改]` 资金执行失败处理：单 Agent 结算、正式工作流统一分账或争议退款广播失败后进入可重试任务，复用同一 raw transaction 和 txHash；未确认前不得把链下状态标成已结算或已退款。
7. [F-007] `[v8 新增]` 正式工作流只有在所有阶段完成、且发布者最终验收后才能创建 `workflow_settle` outbox。链同步必须核对总金额、逐项分账、分账摘要与证据根，任一不一致进入人工复核。
8. [F-008] `[v8 新增]` 仲裁全额退款使用 `dispute_refund`，链同步必须同时核对交易哈希、裁决摘要和证据根；确认后在同一事务更新任务、托管、争议、裁决与 outbox 状态并解除冻结。
7. [F-007] `[v11 修改]` 钱包交互：前端通过 MetaMask 先精确授权任务 USDC，再发起 `deposit`，两笔交易原生 value 均为零；取得 deposit txHash 后若平台登记失败，必须恢复同一 txHash，不得引导重复发送。钱包扩展消息通道无响应时，前端必须在有限时间后解除操作锁并明确提示“结果不确定”；该状态不得登记为链上失败，也不得自动重发。授权回执等待使用独立时限，失败状态的尽力登记不能无限阻塞主操作。本地 Anvil 必须使用 RPC 的 pending nonce 防止钱包跨链实例缓存产生 nonce 空洞，并把准备、授权、存入和登记显示为不同进度；真实测试网与主网仍由钱包管理 nonce。
8. [F-008] `[v12 修改]` 托管金额的唯一来源是已确认 workflow run 的 `quoted_total_minor`，它必须等于全部节点当前报价之和。未完成全部选择、总价为空或任务不处于 `awaiting_escrow` 时，服务端拒绝创建托管 intent；预算偏好不得作为兜底金额。普通 `prepared`、已广播、待确认、已确认或待复核 intent 均锁定选择；只有发布者明确放弃并被服务端记录为 `failed`，且 `deposit_tx_hash` 为空、没有任何链事件时，才重新开放改选。改选事务必须同步更新 intent 金额，后续 retry 只能生成新金额的交易。
9. [F-009] `[v12 新增]` Deposit 哈希登记必须同时提交生成该钱包交易时的 `amountMinor`。仓储仅在该金额等于当前 intent 金额时接受登记；已经改选的旧页面不得把旧报价交易登记为新托管。客户端失败接口只能把尚未广播的 `prepared` intent 标记失败；带 txHash 或链事件的状态只能由链同步、对账和人工恢复流程处理。

## 非功能需求

- 可靠性: 事件监听需处理区块重组（reorg），已处理的事件若因重组失效需能检测并修正，而不是永久保留错误状态。
- 性能: 从交易上链到平台任务状态更新的延迟目标 P95 < 2 分钟；实际延迟由网络出块与分环境确认阈值共同决定。
- 安全: `OPERATOR_ROLE` 的生产签名必须使用 KMS/HSM，不读取明文私钥。当前仓库只实现本地 Anvil 解锁账户适配器，并在生产环境强制失败；KMS/HSM operator client 完成并经目标网络验证前不得上线资金执行。

## 验收标准

- [x] [AC-001] 交易未达到规定确认数前，任务状态不会从「待托管」推进。
- [x] [AC-002] 同一笔交易的事件被处理两次（如服务重启后重复消费）不会导致任务状态重复迁移或对账异常。
- [x] [AC-003] 模拟区块重组场景下，已处理事件若失效可被检测到并阻止错误的状态迁移（或已迁移状态被标记为待核实，而非静默保留错误状态）。
- [x] [AC-004] 链下记录与链上 `escrowOf` 查询结果不一致时，系统产生可被运营看到的告警，而不是静默忽略。
- [x] [AC-005] 退款交易失败后任务状态为「可重试」而非「已退款」，且运营能看到失败原因。
- [x] [AC-006] 中间阶段验收不会创建付款任务；最终验收只生成一笔包含全部 Agent 的统一结算任务。
- [x] [AC-007] DAO/平台仲裁的部分分账或全额退款在链上确认后才解除资金冻结，且所有金额与摘要严格匹配。
- [x] [AC-006] `[v11 修改]` 用户可通过 MetaMask 完成资金托管交易，页面正确展示准备、授权、存入、登记及链上待确认/已确认/失败状态；扩展或授权回执长时间无响应时按钮会恢复并在资金卡片内提示结果仍不确定，平台不会把该情况错误登记为失败或自动重发。本地链重启后即使 MetaMask 缓存旧 nonce，新交易也不会因 nonce 空洞永久停在 queued。
- [x] [AC-007] 重复消费 `MilestoneReleased`/`Finalized` 不会重复累计释放或重复推进终态；链下累计释放额与合约 `releasedAmount` 不一致时产生告警。
- [x] [AC-008] `[v12 修改]` 真实 PostgreSQL 中，部分节点选择不能准备托管；全部节点选定后，intent 金额精确等于节点报价总和。普通 intent 创建后改选被拒绝；明确失败且无 txHash/链事件时可多次改选，节点总价、任务固定价与 intent 金额在同一事务内更新。Deposit 已提交后继续返回 409，托管确认后只派发已选 Agent 并保持下游依赖阻塞。
- [x] [AC-009] `[v12 新增]` 旧页面使用旧 `amountMinor` 登记 Deposit 哈希时返回冲突；失败记录带 txHash、存在链事件或仍处于结果不确定状态时，不得通过“重试”清空哈希或恢复改选。

## 已确认决策

- 链上交易确认阈值继续作为后端配置，不作为首页营销指标。非生产环境中，本地 Anvil 与测试链默认 2 次确认，Ethereum 主网开发默认 6 次；生产部署必须显式设置 `ESCROW_REQUIRED_CONFIRMATIONS`，不得静默继承开发默认值。主网上线仍需结合任务金额、目标延迟和真实网络数据复核配置，高金额任务后续可采用更高阈值。
