# Agent 健康检查与生命周期 — 需求规格

## 概述

管理 Agent 从注册到可接单的状态流转（试运行/可接单/暂停/下架），持续健康检查并在异常时自动暂停派发，运营审核转正式状态。对应 PRD FR-A02、FR-A03。

## 项目信息

- 项目名: ai-agent-collaboration-protocol
- 架构类型: 多服务架构

## 用户故事

- 作为平台，我想要区分 Agent 认证失败、协议不兼容、连接超时和内部错误，以便针对性地暂停派发或提示提供者修复。
- 作为 Agent 提供者，我想要暂停接单而不影响已接任务的继续执行，以便在维护期间不违约。
- 作为运营人员，我想要审核新 Agent 并将其从试运行转为正式状态，且过程可追溯，以便控制新 Agent 带来的质量风险。

## 功能需求

1. [F-001] 健康检查结果分类：区分认证失败、协议不兼容、连接超时、Agent 内部错误四类（复用 [[1.agent-protocol-contract]] 的错误码）。
2. [F-002] `[v3 修改]` 连续失败自动暂停：**仅统计专门的健康检查探测**（不含真实任务执行中的失败，后者由评分和争议机制治理，不进入本计数器）；**仅认证失败、协议不兼容、连接超时三类计入失败**（`Agent 内部错误`不计入——这是业务逻辑失败，与"平台联系不上/协议不兼容"性质不同，不应触发同一套熔断）；**任意一次健康检查成功，失败计数器立即清零**；连续失败达到可配置阈值后，自动暂停向该 Agent 派发新任务。
3. [F-003] 显式状态机：`试运行 → 可接单 → 暂停 → 下架`（暂停可恢复到可接单，下架为终态，需重新注册），非法状态迁移必须被拒绝。
4. [F-004] 未审核、暂停或下架的 Agent 不出现在公开候选列表中（对接 feature 8 的候选过滤逻辑）。
5. [F-005] 暂停接单不影响已接任务继续执行至完成或超时。
6. [F-006] `[v5 修改]` 受控上线期风险上限：Agent 完成 [[15.agent-sandbox-admission]] 的沙箱准入转为 `active` 后，在其 [[12.scoring-system]] 评分样本量达到贝叶斯平滑先验权重（`prior_weight`）之前，视为处于「受控上线期」——单任务预算不得超过平台历史任务预算的某个较低分位数（默认第 30 百分位，可配置），候选列表展示"新入驻"标识；样本量达标后自动解除，不需要人工操作。**不再使用"试运行"指代这个阶段**——`pending_review`（沙箱测试中）状态的 Agent 本来就不会出现在候选列表中，不存在"试运行接真实任务"的场景，容易和受控上线期混淆。
7. [F-007] `[v2 修改]` 转为正式状态必须记录触发条件和审核人，写入审计日志；MVP 的触发条件具体为 [[15.agent-sandbox-admission]] 的沙箱测试清单判定全部通过（不再是笼统的"人工审核通过"，判定依据必须可追溯到具体的沙箱调用记录）。
8. [F-008] `[v4 新增]` 自动恢复：仅**因连续健康检查失败被自动暂停**的 Agent，达到可配置的连续成功阈值后自动恢复为可接单状态，无需人工介入；**提供者主动发起的暂停不适用自动恢复**，必须由提供者显式调用恢复接口，防止"维护中"被健康检查探测误判为"已恢复"而提前把任务派过去。

## 非功能需求

- 性能: 健康检查任务对单个 Agent 的检查间隔可配置，默认 5 分钟一次，不因检查任务本身拖慢派发链路。`[v4]` 检测延迟目标：约 10-15 分钟发现异常并暂停（间隔 5 分钟 × 失败阈值 3 次）；约 10 分钟确认恢复并解除暂停（间隔 5 分钟 × 恢复阈值 2 次）。恢复阈值刻意设置得比失败阈值更保守（需要更多次确认），是为了避免 Agent 在故障边缘反复抖动时暂停/恢复状态来回跳变（flapping）。
- 安全: 审核操作需要运营角色权限校验，普通用户不可调用审核接口。
- 兼容性: 健康检查请求复用 [[1.agent-protocol-contract]] 的签名与超时语义，不另起一套认证逻辑。

## 验收标准

- [ ] [AC-001] 健康检查失败时，返回的失败原因可归类到四类错误码之一，不是笼统的“失败”。
- [ ] [AC-002] 连续失败达到阈值后，该 Agent 不再出现在新的候选列表中，但不影响其已接的进行中任务。
- [ ] [AC-002a] `[v3 新增]` `Agent 内部错误`类的健康检查结果不计入连续失败计数；真实任务执行失败不计入本计数器（只统计专门的健康检查探测）；中间穿插一次健康检查成功会将计数器清零，不是"最近 N 次里失败次数达标"这种滑动窗口口径。
- [ ] [AC-003] 非法状态迁移（如从「下架」直接迁移到「可接单」）被拒绝并返回明确错误。
- [ ] [AC-004] `[v5 修改]` 处于受控上线期（评分样本量未达 `prior_weight`）的 Agent 在候选列表中展示"新入驻"标识；样本量达标后标识自动消失。
- [ ] [AC-005] 每次状态迁移（含自动暂停、人工审核通过）在 `audit_logs` 中留痕，记录触发条件与操作者（自动触发记录为系统操作者）。
- [ ] [AC-006] `[v4 新增]` 因连续失败自动暂停的 Agent，达到连续成功阈值后自动恢复为可接单，无需人工操作；同样的健康检查恢复对提供者主动暂停的 Agent 不产生任何状态变化。
- [ ] [AC-007] `[v4 新增]` 提供者可对自己主动暂停的 Agent 调用恢复接口重新上架；对因健康检查自动暂停的 Agent 调用同一接口应被拒绝并提示"等待自动恢复或联系运营"，防止提供者绕过健康状态直接强行恢复一个仍不健康的 Agent。

## 依赖

- [[1.agent-protocol-contract]]：健康检查请求复用其签名与错误码。
- [[2.agent-registration]]：状态机基于已注册的 Agent 档案运作。
- `[v2 新增]` [[15.agent-sandbox-admission]]：`AdminApprove` 事件由该 feature 的清单判定结果触发（反向依赖：15 调用本 feature 暴露的 `TransitionAgentStatus`，本 feature 不主动依赖 15 的内部实现）。
- `[v5 新增]` [[12.scoring-system]]：**概念依赖，非代码依赖**——受控上线期的判定标准引用其 `prior_weight` 定义，但实际查询代码实现并入 [[7.task-visibility-and-mode]] 的 `ValidateHardConstraints()`，本 feature 不直接调用 12（避免和 12 的开发进度产生阻塞关系，见该 feature 设计模块 4 说明）。
