# 派发与接单确认 — 需求规格

## 概述

将发布者确认（或自动分配）的候选 Agent 以原子方式锁定分配、通过 SQS 派发任务，并处理 Agent 的接单/拒单确认与超时。对应 PRD FR-M02。

> 2026-08-23 体验映射：三步画布仍用于同步比较 9 个工作流 Agent；正式任务详情已经
> 使用本 feature 的 `task_assignments`、签名接单回调与权威任务状态机。两者不冒充同一流程。

- 架构类型: 多服务架构

## 用户故事

- 作为发布者，我想要确认一个候选 Agent 后，系统保证这次分配不会被其他并发请求抢占或重复，以便任务状态清晰可信。
- 作为 Agent 提供者，我想要在规定时间内确认或拒绝派发的任务，超时未响应视为未接单，以便发布者能及时选择其他候选。
- 作为平台，我想要派发请求带幂等键，以便网络重试不会重复创建分配或重复通知 Agent。

## 功能需求

1. [F-001] 候选确认：默认由发布者手动确认一个候选 Agent；若任务开启自动分配（[[7.task-visibility-and-mode]] 的配置），平台按已展示的排序规则自动选择第一候选。
2. [F-002] 原子占用分配：通过条件更新/版本号和唯一约束实现原子占用，多个请求同时确认或抢占同一任务时最多一个成功，其余返回「任务已被分配」，不能仅依赖前端按钮禁用。
3. [F-003] 派发幂等：派发请求携带幂等键（复用 [[1.agent-protocol-contract]] 的幂等规范），网络重试不重复创建分配记录或重复通知 Agent。
4. [F-004] 接单确认：Agent 必须在规定时间内确认或拒绝派发；超时未响应视为未接单。
5. [F-005] 候选切换：Agent 拒绝或超时后，发布者可以选择其他候选（任务回到「待匹配」的候选集合，不要求重新执行完整匹配管道，除非候选集合已过期）。

## 非功能需求

- 一致性: 分配操作必须保证「最多一个成功」的强一致语义，不允许出现同一任务被两个 Agent 同时锁定的中间态。
- 性能: 派发请求从确认候选到 Agent 收到通知的延迟目标 P95 < 10 秒。

## 验收标准

- [x] [AC-001] 并发发起的多个候选确认请求（同一任务）中，最多一个返回成功，其余明确返回「任务已被分配」错误。
- [x] [AC-002] 网络重试导致的重复派发请求不会产生重复的 `task_assignments` 记录。
- [x] [AC-003] Agent 超过规定时限未确认/拒绝时，分配状态自动流转为「接单失败」，任务回到「待匹配」候选集合。
- [x] [AC-004] Agent 拒绝后，发布者可立即看到并选择其他候选，无需等待重新匹配。
- [x] [AC-005] 自动分配模式下，系统选择的候选与匹配阶段展示的排序第一名一致。
