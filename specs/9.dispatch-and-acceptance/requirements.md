# 派发与接单确认 — 需求规格

## 概述

将发布者确认（或自动分配）的候选 Agent 以原子方式锁定分配、通过 SQS 派发任务，并处理 Agent 的接单/拒单确认与超时。对应 PRD FR-M02。

> 2026-08-30 正式工作流映射：每个工作流节点复用 `task_assignments` 的原子占用、签名
> 接单回调与派发重试，并通过 `workflow_node_id` 绑定节点。任务详情只投影持久化候选和
> 最终 assignment，不再维护浏览器内的第二套分配状态。

> 2026-08-31 链路边界：托管前的 candidate selection 只冻结 Agent、候选快照和报价，
> 不创建 `task_assignments`。链上托管确认后才按 DAG 依赖把选择转换为正式 assignment
> 并派发；selection 与 assignment 是两个可审计、不可混用的事实。

## 用户故事

- 作为发布者，我想在付款前确认每个阶段的 Agent 和报价，并确信只有托管确认后平台才会占用和派发这些 Agent。
- 作为 Agent 提供者，我想要在规定时间内确认或拒绝派发的任务，超时未响应视为未接单，以便发布者能及时选择其他候选。
- 作为平台，我想要派发请求带幂等键，以便网络重试不会重复创建分配或重复通知 Agent。

## 功能需求

1. [F-001] `[v4 修改]` 候选确认：正式多 Agent 发布默认由发布者在 `planning` 阶段为每个节点确认候选；服务端只接收 Agent ID，并从加锁的最新候选快照读取报价。任务进入 `awaiting_escrow` 后，无 intent，或 intent 已明确失败且没有 Deposit 哈希和链事件时，发布者仍可更换单个阶段的 Agent；选择不触发 Agent 调用。底层自动分配能力保留给后续显式启用的 AI 选择策略，不作为当前发布页默认值。
2. [F-002] `[v2 修改]` 原子占用分配：链上托管确认后，只有依赖已经满足的节点可将已冻结选择转为 assignment；通过条件更新、版本号和唯一约束保证同一工作流节点最多一条活跃分配。并发请求不能重复占用或派发，不能仅依赖前端按钮禁用。
3. [F-003] 派发幂等：派发请求携带幂等键（复用 [[1.agent-protocol-contract]] 的幂等规范），网络重试不重复创建分配记录或重复通知 Agent。
4. [F-004] 接单确认：Agent 必须在规定时间内确认或拒绝派发；超时未响应视为未接单。
5. [F-005] `[v5 修改]` 候选切换：可在当前候选快照中多次重新选择并覆盖该阶段当前报价；服务端在同一事务内重算工作流总价、任务固定价、失败 intent 金额、版本、事件和审计。`prepared` 必须由发布者在当前 Agent 区就地确认 MetaMask 没有待处理 Deposit，转为可证明未广播的 `failed` 后才能改选；权威状态刷新成功后页面自动展开刚才所选阶段的候选。任何 Deposit 哈希、链事件、结果不确定或后续状态都禁止改选。托管后 Agent 拒绝或超时的替换沿用资金已托管恢复路径。只有候选快照过期或条件改变时才重新执行完整匹配。
6. [F-006] `[v5 新增]` 模式化派发：`aicp_hmac` 继续使用签名请求、异步确认与回调；`http_json` 使用可选 Bearer Token 并同步返回产物。快速结果必须先持久化再确认接单，内部转交失败时只重试转交，不重新调用 Agent。

## 非功能需求

- 一致性: 分配操作必须保证「最多一个成功」的强一致语义，不允许出现同一任务被两个 Agent 同时锁定的中间态。
- 性能: 派发请求从确认候选到 Agent 收到通知的延迟目标 P95 < 10 秒。

## 验收标准

- [x] [AC-001] `[v2 修改]` 并发选择由节点行锁和幂等键串行化，最终只保留一份冻结选择；托管后的并发分配由数据库约束保证同一节点最多一个成功。
- [x] [AC-002] 网络重试导致的重复派发请求不会产生重复的 `task_assignments` 记录。
- [x] [AC-003] Agent 超过规定时限未确认/拒绝时，分配状态自动流转为「接单失败」，任务回到「待匹配」候选集合。
- [x] [AC-004] Agent 拒绝后，发布者可立即看到并选择其他候选，无需等待重新匹配。
- [x] [AC-005] `[v2 修改]` 托管确认后派发的 Agent 必须等于托管前冻结的 `final_selection_agent_id`，不得重新排序后改派第一名；下游节点在依赖满足前不得创建 assignment。
- [x] [AC-006] `[v5 修改]` 真实 PostgreSQL 中，待托管任务更换一个阶段 Agent 后只改变目标节点，总报价按候选快照精确重算并增加任务版本；未广播失败 intent 同步改为新金额并允许继续改选，Deposit 已提交后返回 409。页面在当前 Agent 区完成 prepared 放弃确认并自动展开候选，不把改选入口隐藏在页面底部。
- [x] [AC-007] `[v5 新增]` 快速 Agent 同步结果可跨进程恢复：即使接单已确认后 Marketplace API 暂时失败，恢复处理也读取持久化结果，不重建正文或再次调用外部 Agent；HMAC Agent 既有异步路径保持不变。
