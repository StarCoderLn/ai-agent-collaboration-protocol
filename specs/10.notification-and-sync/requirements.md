# 通知与状态同步 — 需求规格

## 概述

平台到 Agent 的签名异步 Webhook 通知（含退避重试与死信队列）、用户端 SSE 进度推送与断线续传、以及通知失败时的状态补拉能力。对应 PRD FR-M03。

> 2026-08-23 正式体验映射：三步 Agent 编排画布仍负责同步比较候选产物；正式任务详情
> 已接入 `task_events` SSE、浏览器 `Last-Event-ID` 续传和每 5 秒 `/status` 补拉。
> Webhook 由独立 Go worker 从持久化 outbox 投递，画布产物文件不承担传输层状态。

## 用户故事

- 作为平台，我想要向 Agent 的通知使用签名异步机制并在失败时按退避策略重试，最终失败进入死信队列，以便不因单次网络问题丢失通知且不无限重试。
- 作为发布者，我想要通过 SSE 实时看到任务进度，断线后能从上次的位置继续接收，而不是重新收到全部历史事件。
- 作为运营，我想要在通知失败不影响已提交业务状态的前提下，仍能通过补拉接口获取当前真实状态。

## 功能需求

1. [F-001] Webhook 通知：平台到 Agent 使用经签名的异步 Webhook/任务 API（复用 [[1.agent-protocol-contract]] 签名规范）；失败按退避策略重试，达到上限进入死信队列。
2. [F-002] SSE 进度推送：用户端优先使用 SSE 展示任务进度，断线后可依据事件游标续传；轮询作为降级方案。
3. [F-003] 事件结构：每个事件包含事件 ID、任务 ID、状态版本和产生时间，重复事件可安全忽略。
4. [F-004] 失败隔离：通知失败不直接回滚已经提交的业务状态；平台必须提供补拉当前状态的接口。
5. [F-005] 运营可查询：派发/通知失败原因和重试次数对运营可查询（供 [[14.ops-backend-and-metrics]] 使用）。

## 非功能需求

- 可靠性: 死信队列达到上限后必须产生告警，不允许静默丢弃失败通知。
- 一致性: 事件的状态版本必须单调递增，接收方可据此判断是否为过期或重复事件。

## 验收标准

- [x] [AC-001] Webhook 通知失败后按退避策略重试，达到重试上限的通知进入死信队列并可查询。
- [x] [AC-002] SSE 连接断开后重新连接并携带上次的事件游标，只收到游标之后的事件，不重复推送历史事件。
- [x] [AC-003] 重复投递的同一事件（相同事件 ID）被接收方安全忽略，不产生重复的状态更新。
- [x] [AC-004] Webhook 通知失败时，任务的业务状态（如已提交的进度）保持不变，且可通过补拉接口查询到当前真实状态。
- [x] [AC-005] 运营可查询到指定任务的通知失败原因与重试次数。
