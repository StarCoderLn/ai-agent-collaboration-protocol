# Ethereum 托管合约 — 需求规格

## 概述

实现资金托管、结算、退款和紧急暂停的 Ethereum 智能合约，是任务资金流的链上事实来源。对应 PRD FR-T03 的链上部分与 PRD §11 P3 的 SC-E 交付物。

## 项目信息

- 项目名: ai-agent-collaboration-protocol
- 架构类型: 多服务架构（Solidity 合约层）

## 用户故事

- 作为发布者，我想要将资金托管进合约后，只有满足验收/仲裁条件才会被结算或退款，以便信任平台不会擅自处置我的资金。
- 作为平台，我想要一个仅限授权地址触发结算/退款的合约，以便业务规则（验收、仲裁）在链下决定，链上只忠实执行已授权的资金动作。
- 作为安全负责人，我想要合约在上线前完成独立审计并具备紧急暂停能力，以便在发现漏洞时能及时止损。

## 功能需求

1. [F-001] 存款托管：发布者为指定任务存入资金，合约记录任务 ID、金额、支付方，状态置为「已托管」。
2. [F-002] `[v6 修改]` 结算：仅平台授权地址可触发；Agent 提供者收到 `agentGrossAmount − feeAmount`，平台收到 `feeAmount`，托管上限与实际成交额的差值 `escrowAmount − agentGrossAmount` 原路退给发布者。手续费仍由 Agent 提供者承担，三笔资金之和必须严格等于原托管额。
3. [F-003] 退款：仅平台授权地址可触发，因取消/超时/仲裁向发布者退款。
4. [F-004] 紧急暂停：合约具备 `pause`/`unpause` 能力，暂停期间拒绝新的存款、结算、退款操作。
5. [F-005] 事件接口：`Deposited`、`Released`、`Refunded`、`Paused`、`Unpaused` 事件携带足够信息供链下同步（feature 6）。
6. [F-006] 幂等与防重放：同一任务 ID 不可重复存款（除非先前托管已被结算/退款），同一任务的结算/退款操作不可重复执行。

## 非功能需求

- 安全: 使用 checks-effects-interactions 模式与重入保护；关键函数（存款、结算、退款）需要专门的重入攻击测试用例；合约在生产部署前必须完成独立第三方审计，严重问题需关闭后才可上线（PRD §13 上线验收清单）。
- 权限: 结算与退款操作仅限平台授权地址（多签或角色控制，具体权限模型待确认，见开放问题）触发，发布者/Agent 提供者无法直接调用。
- 可观测: 所有资金动作必须产生事件，链下（feature 6）依赖事件而非轮询状态变量。

## 验收标准

- [x] [AC-001] 非授权地址调用结算或退款函数时被拒绝（revert）。
- [x] [AC-002] 同一任务 ID 的资金在已结算或已退款后，无法再次被结算或退款。
- [x] [AC-003] 合约暂停状态下，存款、结算、退款操作均被拒绝，暂停/恢复操作本身不受影响。
- [x] [AC-004] 模拟重入攻击的测试用例无法造成超额转账或状态不一致。
- [x] [AC-005] 每次存款、结算、退款、暂停/恢复都产生对应事件，事件参数包含任务 ID、涉及地址和金额。
- [x] [AC-006] 合约完成至少一轮内部安全测试（含重入、权限、暂停边界用例）；独立第三方审计为上线前置条件，不在本 feature 开发阶段完成，但需在 tasks 中标注为后续里程碑依赖。
- [x] [AC-007] 托管额高于实际成交额时，Agent 净收入、平台手续费和发布者差额退款之和严格等于托管额；成交额不得超过托管额，手续费不得超过成交额。

## 依赖

- 无前置 feature 代码依赖（可与 feature 1-4 并行开发）；`[v2]` `feeAmount` 的计算规则权威定义在 [[4.task-creation-and-preview]] 的 `CalculatePlatformFee()`，合约本身不感知费率，只接收计算好的金额（见下）。

## 开放问题

- ~~平台手续费费率是否为 0.4%、由哪方承担~~ `[v2 已确认]`：费率 0.4%，见 [[4.task-creation-and-preview]] F-005。**合约本身不需要跟着改**——`feeAmount` 一直是由链下计算好后作为参数传入 `release()`（见 design.md 技术决策"手续费金额由调用方传入而非合约内置公式"），费率数字只影响链下计算逻辑，合约代码不需要感知具体费率是多少。
- ~~合约升级权限与私钥管理方案未定~~ `[v4 拆分]`：这原本是两个问题，分开看：
  - **合约升级权限**——`[v1 已确认]` 采用**不可升级的简单合约 + 可暂停**方案，不引入代理合约模式，降低攻击面；这不是还悬着的问题，只是此前和私钥管理写在同一条里显得像是一起没定。
  - **私钥管理方案**——`[v5 已确认架构与阈值参考]`：拆成三个独立角色，按风险特征分别托管（design.md 模块 3）：`PAUSER_ROLE`（暂停/恢复）用多签，优化响应速度；`OPERATOR_ROLE`（结算/退款）因需自动化高频调用，由后端服务持有但要求 KMS/HSM 托管私钥、不落地明文；`TREASURY_ROLE`（手续费收款地址变更）用多签，优化审慎程度而非速度。多签签名人数量参考行业惯例（Aave 等协议的公开实践），按合约实际托管资金规模（TVL）分级，**不是固定不变的数字**：

    | 托管资金规模（TVL） | `PAUSER_ROLE`（优化速度） | `TREASURY_ROLE`（优化审慎） |
    | --- | --- | --- |
    | 100 万美元以下（MVP 早期） | 3-of-5 | 4-of-7 |
    | 100 万-1000 万美元 | 4-of-7 | 5-of-9 |
    | 1000 万美元以上 | 5-of-9 | 更高，需专项评估 |

    `TREASURY_ROLE` 在同一资金规模档位下比 `PAUSER_ROLE` 多一档签名人数——参考 Aave 的实际配置（Protocol Emergency Guardian 4-of-7 更快响应，Governance Emergency Guardian 5-of-9 更审慎），"响应速度优先"和"审慎程度优先"两种角色在同等资金规模下本来就该有不同的人数要求。**具体签名人名单是部署时的运维决策**，不在本 feature 合约代码的设计范围内，但档位表可以作为选人数量的直接依据，不需要每次都重新调研；托管资金规模变化时，按上表调整多签配置，不需要改合约代码（多签的人数和阈值是多签合约自身的配置，不是本合约的一部分）。
- 接单后取消、返工、超时赔付的资金处理规则待确认（PRD §14 P0-4），本设计的退款函数支持任意授权发起的退款，具体业务判定逻辑在链下（feature 6、10、12）实现，合约本身不内置这些规则。
