# V0 匹配与候选列表 — 需求规格

## 概述

实现「分类过滤 → 资格过滤 → 标签匹配 → 规则排序」的可解释匹配链路，生成候选 Agent 列表与可追溯的 `JobDistributionRecord`。对应 PRD FR-M01。

> 2026-08-31 正式工作流映射：任务发布后、托管前，每个节点按分类、标签、资格和
> 可用性执行本 feature 的权威匹配并持久化候选快照。匹配阶段可选预算上限只是排序
> 偏好，不隐藏报价略高的候选；用户选完所有节点后才汇总准确总价。平台每个节点最多展示 3 个候选，
> 但托管确认后只派发最终选择的 1 个 Agent。

## 项目信息

- 项目名: ai-agent-collaboration-protocol
- 架构类型: 多服务架构

## 用户故事

- 作为发布者，我想要从综合推荐、质量优先和性价比优先三个视角比较候选，并看到样本量、相似任务和案例来源，以便判断推荐是否可信，而不是只看一个综合分。
- 作为平台，我想要每次匹配都留下可追溯的记录（候选集、过滤原因、排序结果、规则版本），以便复现历史匹配结果和排查匹配异常。
- 作为发布者，当没有候选 Agent 时，我想要知道主要限制条件是什么，以便调整任务后重新匹配。
- 作为发布者，我想先看候选组合价格区间，再决定是否设置预算上限；如果平台识别的能力不准确，我可以在选人前修正并重新推荐。

## 功能需求

1. [F-001] `[v4 修改]` 匹配链路：分类过滤 → 资格过滤（健康/准入状态、币种、截止时间等硬约束）→ 能力标签软匹配 → 规则排序。可选预算上限按节点权重拆成价格偏好并参与排序，但不得成为资格过滤或托管金额。候选卡完整展示报价，用户选择后由服务端计算准确总价。
2. [F-002] `[v6 修改]` 候选展示字段：已匹配能力、尚未覆盖能力、报价、预计时长、综合评分、历史完成量、**新 Agent 标识（仅 0 个真实结算任务）**，以及任务匹配度、评分样本、相似任务完成量、按时交付率、返工率、Agent 责任争议率、当前负载、五维评分和置信度。候选快照标出综合推荐、质量优先、性价比优先徽标；切换比较视角不修改冻结快照。
3. [F-003] `[v4 修改]` 无候选处理：说明硬限制条件（如无可用 Agent、币种或截止时间不符）并允许重新匹配。能力未命中只降低排序并显示“尚未覆盖”，预算不足只提示当前最低组合高于偏好，不得直接产生空候选。
4. [F-004] 可复现性：相同输入和相同规则版本必须产生相同的候选集合与排序结果；每个候选展示简短匹配理由。
5. [F-005] `JobDistributionRecord`：每次匹配持久化任务快照、候选集、过滤原因、特征值、排序结果、规则版本、最终选择。
6. [F-006] 排序规则版本化：排序权重（匹配度、质量、价格、响应速度、负载、历史完成量）可配置且有版本号，具体权重数值待产品确认。
7. [F-007] `[v3 新增]` 案例证据最多随候选快照返回 3 条，优先展示同类公开任务中已验收的正式制品，再补充 Agent 提供者上架时提交的公开案例。两类来源必须分别标记为“平台已验证交付”和“Agent 自行提供”；非 HTTP(S) 的内部制品引用只展示摘要，不生成浏览器外链。
8. [F-008] `[v4 新增]` 能力修正：工作流节点处于 `selecting` 且尚未选择 Agent 时，发布者可增删最多 10 项能力。服务端统一执行同义词归一、禁用词和字符边界校验，写入审计与节点事件后只重匹配该节点；任何节点已选后，整单预算偏好锁定，已选节点能力也锁定。
9. [F-009] `[v5 新增]` 关系图：未选择阶段可显示冻结候选；阶段选定后默认只显示该阶段最终选择并高亮连接，已成立的阶段依赖使用高亮流动虚线。发布者点击重新选择时才展开目标阶段全部冻结候选，取消或确认后重新收敛，其他阶段保持不变。
10. [F-010] `[v7 新增]` 统一标签语言：任务自然语言识别、Agent 创建、Agent 编辑和提供者案例必须读取同一数据库词表，将常见中英文同义表达收敛为 canonical 标签。历史候选快照不可重写；词表修复后通过显式重新匹配生成新证据。

## 非功能需求

- 性能: 从工作流节点进入 `selecting` 到生成候选列表的耗时目标 P95 < 5 秒；多个独立节点允许并行生成候选，不要求等托管后再串行匹配。
- 数据源: V0 分类与标签继续存储在 PostgreSQL；V1 复用同一实例的 pgvector 扩展，不引入
  独立向量数据库或新的运维边界。

## 验收标准

- [x] [AC-001] `[v4 修改]` 不可用、币种不符或无法按时交付的 Agent 不出现在候选列表中；报价超过预算偏好、某项能力未命中不得导致候选被过滤。
- [x] [AC-002] `[v3 修改]` 候选项展示三种推荐视角、报价、匹配度、样本量、相似任务、按时率、返工率、责任争议率、五维评分和置信度，且来源于持久化候选快照而非前端临时拼接。
- [x] [AC-003] 无候选时提示具体限制条件，且修改任务字段后可重新触发匹配并生成新的 `JobDistributionRecord`。
- [x] [AC-004] 用相同任务快照和相同规则版本重复执行匹配，得到完全相同的候选集合与排序结果。
- [x] [AC-005] 每次匹配的 `JobDistributionRecord` 可查询到完整的候选集、过滤原因、特征值、排序结果和规则版本。
- [x] [AC-006] `[v3 新增]` 候选案例优先使用平台已验收的同类公开制品，并与 Agent 自行提供案例显示不同来源；自行提供案例不增加平台已验证完成量，内部或非法地址不生成外链。
- [x] [AC-007] `[v4 新增]` 预算偏好可留空，合法修改后重新生成未选择节点候选，但 `budget_cap_minor`、`agreed_amount_minor`、`quoted_total_minor` 和托管 intent 均不变；选人后修改返回明确冲突。
- [x] [AC-008] `[v4 新增]` 用户可查看并修正平台识别能力；候选分别展示已覆盖和未覆盖能力，能力修改有所有权、幂等、状态锁和审计证据。
- [x] [AC-009] `[v5 新增]` 已选阶段关系图不继续展示未选候选；重新选择会展开原冻结候选，并明确区分当前选择和可更换项，取消后恢复收敛视图。
- [x] [AC-010] `[v7 新增]` 使用“学术研究”“文献检索”或“论文写作”上架、编辑 Agent 时均保存为 `research`；既有 Agent 与案例完成前向回填，既有 `JobDistributionRecord` 保持不变。

## 开放问题

- 排序权重的具体数值待产品确认（PRD §14 P1-2），当前以可配置项 + 默认权重实现，避免权重未定阻塞匹配链路结构开发。
- ~~候选可视化的脑图式展示~~ `[v5 已实现]`：使用 React Flow 投影任务阶段、冻结候选和最终选择；图仅用于查看与聚焦阶段，不能拖拽改写正式 DAG。

## V1 向量检索（已完成）

- Agent 使用 `tags + capability_desc`、任务使用 `tags + description` 生成 OpenAI
  `text-embedding-3-small` 1536 维向量；Agent 向量按内容哈希惰性回填，任务正文不落入
  长期向量表。
- PostgreSQL + pgvector 执行 Top-k；V0 健康、准入、币种和截止时间硬约束先执行，
  向量只从合格 Agent 中召回，候选内继续由 V0 版本化规则排序。
- OpenAI、向量缓存或查询失败时保存稳定错误类别并返回完整 V0 候选；fallback 指纹与
  V1 成功指纹分离，后续请求不会被历史 fallback 永久阻断。
- 真实隔离端到端链路已验证 1536 维响应、向量缓存、Top-k 和候选快照；pgvector 查询
  为 4.111ms，低于 50ms 目标。

## 后续版本边界

- **V2 反馈学习排序（未实现）：** 持续回写“分发为候选 → Agent 接单 → 最终成功”反馈，
  使用梯度提升模型训练 CTR 排序器，并在夜间离线更新。这里的“在线学习”指线上持续
  收集反馈，模型参数不在用户请求内实时更新；新模型必须版本化、评估后发布并支持回退。
- 点击、查看详情、CVR 或其他推荐特征不属于当前已确认的 V2 必需输入；如后续需要扩展，
  必须经过独立产品变更，不能替代上述三段权威反馈。
