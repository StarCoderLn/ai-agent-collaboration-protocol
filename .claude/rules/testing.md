# Testing

## 当前阶段状态

- 项目仅有 `docs/`、`specs/`(16 个 feature 的 requirements.md/design.md/tasks.md)与 `PLAN.md`,尚无 `package.json`/`go.mod`/`Cargo.toml`/`pyproject.toml` 等技术栈文件,也没有测试框架、测试目录或 CI 测试配置。
- 不得虚构测试命令、测试框架名称或覆盖率数字。技术栈和测试工具一旦由用户决策或工作流(如 `yd:prd`/`yd:ai`)产出,应增量补充本文件,不得覆盖本节已有内容。

## 验证原则(AGENTS.md 强制门禁)

- 验证强度与风险相称:局部修改执行最接近改动的验证;高影响修改(公共接口、数据 schema、认证、资金、并发、部署、跨系统流程)需验证正常路径、边界条件、失败路径及相关回归。
- 不得声称未实际执行的验证已经通过。当前阶段没有可运行的测试命令时,必须明确说明"未执行测试,原因:项目尚无测试框架/代码实现",并列出用户后续可执行的验证方式(如人工审阅 requirements/design/tasks 文档、走查验收标准)。
- 完成任务前,运行适用范围内的完整测试、类型检查、lint 或构建;当前阶段这些均不适用时,以文档一致性检查(specs 与 PLAN.md 是否冲突、验收标准是否可核验)替代。

## 进入编码阶段后必须补充的内容

一旦技术栈确定并开始实现,应在本文件追加(不覆盖以上内容):

- 实际测试命令(单元/集成/端到端)及其在 `.claude/rules` 或项目根的调用方式。
- 测试文件组织约定与命名规则。
- 高影响改动(认证、资金、并发、状态迁移)所需的最低测试覆盖要求。
- Mock/Stub 使用边界:占位凭据或模拟数据不得作为"任务已完成"的证据。
