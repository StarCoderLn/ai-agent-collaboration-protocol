# 工程方法论：解释、设计与重构

本文提炼《无穷的开始》《软件设计的哲学》和《重构（TypeScript 版）》中最适合软件开发的思想。它解释项目规则为什么存在；强制执行要求以根目录 `AGENTS.md` 为准。

## 1. 三个层次，一个循环

三本书分别解决三个不同层次的问题：

| 层次 | 要回答的问题 | 核心方法 |
| --- | --- | --- |
| 认识问题 | 我们凭什么认为理解正确？ | 猜想、好解释、批评、反例和纠错 |
| 设计系统 | 如何让知识不扩散成复杂度？ | 深模块、信息隐藏、简单接口和一致性 |
| 演进代码 | 如何安全地持续改善设计？ | 行为保护、小步重构和持续验证 |

统一循环是：

> 发现问题 → 提出解释 → 明确不变量 → 设计边界 → 小步实现或重构 → 验证反例和失败路径 → 沉淀知识 → 发现下一个问题

## 2. 《无穷的开始》：可纠错的知识增长

### 2.1 问题不可避免，但可以解决

不存在没有问题的最终架构。每个解决方案都会改变环境、扩大能力，也会暴露更深的问题。工程上的成熟不是让问题消失，而是让系统和团队持续发现、解释并修正问题。

这意味着：

- 不把当前框架、架构和需求视为终局。
- 不因存在缺陷就否定所有进展，也不因当前可用就停止纠错。
- 将监控、测试、回滚和复盘视为产品能力，而不是发布后的补救手续。

### 2.2 知识来自猜想与批评

观察不会自动生成设计。日志能显示某次调用超时，却不能自行解释是容量、锁竞争、上游故障还是错误的重试策略。团队必须提出候选解释，并设计能够区分它们的证据。

工程流程应当是：

1. 列出已验证事实。
2. 提出能解释事实的候选机制。
3. 寻找它们预测不同结果的地方。
4. 用最小实验、日志、测试或代码检查进行区分。
5. 淘汰错误解释，而不是只收集支持首选方案的证据。

### 2.3 好解释难以随意改变

好解释的细节被问题和证据约束，不能随手替换后仍然成立。坏解释通常具有这些特征：

- 任何结果都能事后解释。
- 需求变化后不断增加特殊分支。
- 只能引用权威、流行框架或历史惯例。
- 无法说明什么证据会推翻它。

在软件设计中，如果同一个概念需要越来越多布尔开关、例外状态和局部补丁，通常应重新检查领域模型，而不是继续堆条件。

### 2.4 可错论与乐观主义

所有知识都可能出错，但这不等于相对主义。相反，结论越重要，越需要清晰陈述、严格检验和可恢复设计。

乐观主义也不是承诺任何任务都能立即完成，而是相信可以创造缺失的知识。遇到未知时，应把它转化为可回答的问题、实验或观测信号；同时诚实说明时间、权限和真实环境限制。

### 2.5 权威与经验的正确位置

文档、资深意见、框架惯例和 Agent 输出都是有价值的知识来源，但不能保证正确。经验用于批评和检验解释，不能替代因果模型。

因此：

- 代码与实际行为不一致时必须指出。
- 评审针对解释和证据，不针对提出者身份。
- “最佳实践”必须说明它在当前约束下解决了什么问题。

## 3. 《软件设计的哲学》：复杂度管理

### 3.1 复杂度的三个症状

1. **修改扩散：** 一个简单需求需要同时修改许多模块。
2. **认知负担：** 完成局部工作前必须理解大量无关知识。
3. **未知的未知：** 开发者不知道哪些地方需要修改，也不知道哪些依赖会被破坏。

复杂度会累积。单个捷径看似便宜，但反复选择战术修补会让每次修改都更慢、更危险。

### 3.2 战略编程

战略编程不是提前构建庞大框架，而是在日常开发中持续投入少量成本，使接口、模块、命名、测试和错误语义保持清晰。其目标是让后续功能更快，而不是追求抽象数量。

### 3.3 深模块

模块深度可以理解为“隐藏的功能与复杂度”相对于“暴露的接口复杂度”。深模块用较小接口提供较强能力；浅模块让调用方承担大量配置和内部知识。

判断一个新抽象是否有价值，应询问：

- 它隐藏了哪些复杂决策？
- 调用方少知道了什么？
- 未来变化会集中在这里，还是仍扩散到所有调用方？
- 如果移除这一层，系统是否几乎没有变化？

### 3.4 信息隐藏与信息泄漏

同一设计知识应只有一个权威位置。信息泄漏不等于代码文本重复：两个模块即使代码不同，只要都知道同一格式、状态含义或协议规则，仍然需要同步修改。

时间顺序不是理想模块边界。按“读取 → 处理 → 写入”拆模块，可能让同一领域规则贯穿所有阶段；应优先按隐藏的知识和变化原因划分职责。

### 3.5 把复杂度向下吸收

如果模块内部多做一些工作能让大量调用方更简单，应由模块承担复杂度。例如重试、默认值、序列化、舍入和兼容逻辑应尽量封装在负责该知识的边界内，而不是让每个调用方重复配置。

这不等于制造上帝类。模块只吸收与其隐藏知识相关的复杂度，内部仍应有清晰结构。

### 3.6 适度通用与投机抽象

通用性应来自多个真实用例共享的机制。好的通用接口往往比专用接口更简单、更深；坏的通用框架充满未被当前需求约束的参数、钩子和扩展点。

判断标准不是“未来可能用到”，而是它是否已经简化当前接口和多个真实调用方。

### 3.7 不同层应有不同抽象

上层只是改名后转发下层调用，会增加层数而没有隐藏知识。服务、适配器、仓储和包装器必须提供不同抽象，例如稳定领域契约、错误转换、缓存、幂等或兼容策略。

### 3.8 定义错误不存在

最好的异常处理有时是通过契约消除异常。例如幂等删除可以把“已不存在”定义为成功状态。但这不等于吞掉错误：真正的失败仍需携带上下文、可观测并具有恢复路径。

### 3.9 设计两次与注释先行

关键接口不要被第一个想法锁定。至少形成两个真正不同的设计，比较接口深度、信息泄漏、修改扩散、可测试性和恢复方式。

在实现前尝试写出公开契约和关键不变量。如果无法简洁说明模块做什么、隐藏什么以及失败时如何表现，往往说明抽象还不清晰。

## 4. 《重构（TypeScript 版）》：受保护的演进

### 4.1 重构的定义与两顶帽子

重构是在不改变外部可观察行为的前提下调整内部结构。增加能力时戴“功能帽子”，只改变行为；改善结构时戴“重构帽子”，只调整结构。两种活动可以频繁交替，但每一步的目的和验证标准必须明确。

### 4.2 小步与行为基线

大重构应由许多可理解、可验证、可回退的小变换组成。旧系统行为不清楚时，先用特征测试记录当前行为；它不证明当前行为正确，只防止无意改变。

典型节奏是：

1. 建立或运行最小行为基线。
2. 做一种结构变换。
3. 运行最快的相关验证。
4. 提交到安全检查点或继续下一小步。
5. 完成局部目标后运行更完整验证。

### 4.3 坏味道不是机械规则

重复代码、长函数、数据泥团、基本类型偏执、特性依恋、中间人、消息链、霰弹式修改、发散式变化和复杂条件都值得调查，但同一表象可能有不同根因。

重构手法应服务于明确目标：

| 目标 | 常见手法 |
| --- | --- |
| 让意图清晰 | 改名、提炼变量、提炼函数 |
| 集中领域知识 | 移动函数、移动字段、封装变量 |
| 表达领域概念 | 引入参数对象、值对象、领域类型 |
| 分离流程阶段 | 拆分阶段、分离查询与修改 |
| 控制状态复杂度 | 可辨识联合、显式状态机、以多态替代条件 |
| 移除无价值层级 | 内联函数、内联类、移除中间人 |

能够用局部提炼解决的问题，不要直接升级为新框架或复杂继承体系。

### 4.4 TypeScript 的帮助与边界

TypeScript 能在改名、移动和签名调整时提供快速反馈，但类型检查无法证明：

- 外部 JSON 在运行时符合类型声明
- 金额精度、状态迁移和权限规则正确
- 数据库事务、队列和回调不存在竞态
- 第三方服务、网络和时间相关行为可靠

因此应使用严格类型、运行时 schema 校验、可辨识联合、领域类型和分层测试共同保护重构。`any` 和不受约束的类型断言会破坏这张安全网。

### 4.5 重构与性能

清晰结构使性能热点更容易测量和隔离。先用基准、追踪或 profiling 找到瓶颈，再对热点进行针对性优化；不要以未经测量的性能担忧拒绝改善整体结构。

## 5. 常见误读

- “一切都可能错”不等于没有标准；它要求更明确的解释和更严格的检验。
- “问题能够解决”不等于可以忽略资源、权限和时间限制。
- “战略设计”不等于先建平台或框架；它的目标是更少、更深的接口。
- “通用模块”不等于万能模块；通用性必须来自真实共享机制。
- “吸收复杂度”不等于上帝类；模块只隐藏属于自己的知识。
- “定义错误不存在”不等于吞掉错误；真正失败必须可见、可诊断、可恢复。
- “重构不改变行为”不等于测试通过便绝对安全；测试覆盖始终有限。
- “小步重构”不等于无休止整理；重构必须服务当前目标并在达到验收后停止。
- “代码自解释”不等于不写注释；注释应解释意图、不变量和反直觉原因。
- “最佳实践”不构成理由；必须说明它如何约束当前问题并用什么证据验证。

## 6. 对本项目的直接启示

本项目把外部 Agent、钱包、链服务和用户输入连接到资金与任务状态，因此最重要的设计知识必须集中：

- 用显式状态机表达任务、托管、交付、验收、争议和结算。
- 用领域类型和统一算法处理金额、币种、费率、精度与舍入。
- 把认证、授权、任务归属和数据可见性放在可信边界。
- 把外部 Agent 输出视为不可信输入，并限制其工具和数据权限。
- 对回调和链上结果设计认证、幂等、重放防护、超时、补偿与人工恢复。
- 用契约测试固定跨系统协议，用审计日志保留高风险操作证据。

这些不是附加功能，而是决定平台是否可信的核心领域模型。
