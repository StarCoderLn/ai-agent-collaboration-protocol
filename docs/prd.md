> 文档状态：MVP 当前基线
>
> 目标读者：产品、设计、前端、后端、算法、合约、测试与运营

## 1. 产品概述

### 1.1 产品定位

平台是一个 AI Native 的去中心化任务分发与协作平台，连接两类参与者：

- 任务发布者：提交任务和截止时间，在匹配阶段确认预算与 Agent，并验收结果。
- Agent 提供者：注册运行在自有服务器上的 Agent，接受任务并获得报酬。

平台主要负责 Agent 发现、任务匹配、执行调度、过程追踪、结果交付、资金托管和争议
处理。第三方 Agent 仍运行在提供者自己的环境中，平台只通过统一协议调用，不托管其
代码、模型或运行环境。平台可以运营自建参考 Agent；当前已有 Stagehand 网页调研助手、
论文调研 Agent 和正式 PRD、设计、Coding Agent，既用于协议联调与质量比较，也可以在通过同一准入和派发边界后
承接真实任务，不改变“生态 Agent 主要由第三方提供”的定位。

### 1.2 核心价值

- 发布者不需要理解 Agent 的实现细节，也能完成从需求发布到结果验收的全过程。
- Agent 提供者通过统一协议接入平台，获得任务与收入。
- 平台通过准入、试运行、匹配、监控、评分和仲裁，提高交付质量与交易可信度。
- 对复杂任务，平台能识别多 Agent 协作需求，并提供可理解、可调整的工作流建议。

### 1.3 MVP 目标

MVP 验证以下核心闭环：

1. Agent 提供者可以注册一个可被平台安全调用的 Agent。
2. 发布者可以创建任务并完成资金托管。
3. 平台可以基于分类和标签推荐候选 Agent，并将任务派发给选定 Agent。
4. 平台可以追踪执行状态，接收最多 3 个候选结果并交付给发布者。
5. 发布者可以验收、评分或发起争议；系统能够完成结算或退款。

### 1.4 MVP 成功指标

| 指标 | 定义 | 目标值 |
| --- | --- | --- |
| 任务成功交付率 | 在截止时间内进入“待验收”的任务数 / 已派发任务数 | 待确认 |
| 首次验收通过率 | 未返工、未争议即通过的任务数 / 已验收任务数 | 待确认 |
| 任务争议率 | 发起争议的任务数 / 已交付任务数 | 待确认 |
| Agent 接单成功率 | Agent 接受的任务数 / 向其派发的任务数 | 待确认 |
| 平均匹配耗时 | 从任务可匹配到产生候选列表的平均时长 | 待确认 |
| 平均交付周期 | 从 Agent 接单到首次提交结果的平均时长 | 待确认 |

## 2. 范围与边界

### 2.1 MVP 范围

- Agent 注册、凭证配置、连通性验证、自动准入与上下架。
- 任务创建与截止时间设置、匹配阶段预算确认、资金托管。
- 最终匹配 V2：资格与资金硬约束、Embedding/pgvector 召回、Wide & Deep + ESMM 排序，以及候选 Agent 推荐。
- “平台推荐、用户确认”的辅助分配模式；自动分配仅在发布者显式开启时使用。
- 公开任务市场与“我的任务”工作台分离，发布者可控制任务可见性。
- 单 Agent 任务的派发、状态追踪、超时处理与结果交付。
- 正式多 Agent 工作流：按任务类型规划节点，逐节点匹配、执行和质量验收，最终由发布者一次验收并统一结算。
- 每次任务最多提交 3 个候选结果，由发布者选择其一验收。
- 基础五维评分。
- 争议发起、证据提交、平台/DAO 仲裁与多 Agent 统一结算或退款。
- 工作台钱包资产概览：按各资产所在网络展示 ETH、USDC 和产品 YD 可用余额；只读余额不依赖 MetaMask 当前连接网络。

#### 2.1.1 正式任务驱动的设计 → Coding 工作流（2026-09-06 更新）

软件开发任务使用以下正式串行节点；节点、分配、制品和验收均持久化：

1. 发布者提供任务标题、服务分类和截止日期，补充说明可选。平台沿用确定性规则推荐执行方案，不调用模型免费生成完整 PRD，也不默认增加收费 PRD 节点。
2. 用户先选择 Agent、确认执行范围和准确总价，再托管；缺少主题或用途的明确空泛请求在发布页就近提示补充。未指定的呈现细节由 Agent 合理补足，与用户明确需求区分；页面不设置额外的自由发挥开关，也不向任务说明追加授权文案。
3. 设计 Agent 通过 `TaskContract` 接收原始任务，交付结构化 DesignSpec；平台可信渲染器
   根据同一规范生成 1440 桌面端与 390 移动端设计稿，供发布者直观验收。
4. 设计制品通过机器门禁后解锁 Coding 节点，此时记录质量事实但不释放资金。
5. Coding Agent 同时接收需求、完整 DesignSpec 与桌面/移动设计稿，成对交付 TSX 和响应式
   CSS；平台校验信息层级、可见文案、视觉 token、响应式规则与样式安全后，再装配运行说明和
   测试计划。
6. 发布者在大尺寸隔离预览中检查最终制品，可选择返工、发起争议或最终验收；最终验收后一笔交易统一分配全部 Agent 收入、平台费和未使用预算。

三类候选均包含 DeepSeek 直连、Mastra 编排、自研状态机三种实现，使用同一模型和相近
预算作为控制变量。每个节点只执行最终分配的一个 Agent，不默认产生三倍调用成本。
图片、视频、研究和通用任务直接生成单个交付节点；独立设计也不附加开发。只有用户本来发布的就是 PRD 服务需求，才匹配 PRD Agent，不增加“购买 PRD”开关或推销入口。历史工作流按原有节点、输入契约和报价继续执行，不迁移其托管或结算记录。

## 3. 角色与权限

| 角色 | 核心能力 | 关键限制 |
| --- | --- | --- |
| 任务发布者 | 创建任务、托管资金、选择 Agent、查看过程、选择结果、验收、评分、发起争议 | 只能操作自己发布的任务 |
| Agent 提供者 | 注册 Agent、配置接口与报价、上下架、查看任务、提交结果、查看结算 | 不得查看未分配给自己的私密任务数据 |

## 4. 核心业务流程

### 4.1 Agent 入驻

1. 提供者连接钱包并创建 Agent 档案。
2. 填写名称、分类、能力描述、标签、报价、预计响应时间和服务地址。
3. 如服务需要鉴权，配置可选访问密钥；密钥必须加密保存，不得在页面或日志中明文展示。
4. 平台自动执行 3 次不同的标准试运行，记录协议、连接和产物技术指标。
5. 技术门禁通过后，平台用一次 AI 调用批量评测三份产物，并按固定阈值自动决定是否上架。
6. 未通过时提供者可查看原因并重新验证；通过后 Agent 进入“可接单”状态。
7. 提供者可以暂停接单或下架 Agent。

### 4.2 单节点任务闭环（MVP）

1. 发布者填写任务信息并提交。
2. 平台校验截止时间和必填项，建立单节点工作流并生成候选 Agent 列表。
3. 页面展示匹配理由、报价、预计时长和历史质量，由发布者确认一个候选 Agent。
4. 平台在事务内锁定 Agent 与准确报价，任务进入“待托管”。
5. 发布者将准确金额存入智能合约，链上确认后平台派发任务并等待 Agent 接单。
6. Agent 接单后开始执行，并按协议上报状态、在截止时间前提交结果。
7. 发布者检查结果，并进行验收、要求返工或发起争议。
8. 验收通过后，合约扣除平台服务费并向 Agent 提供者结算；任务结束后发布者进行评分。

### 4.3 正式多 Agent 任务

1. 发布事务按任务分类、标签和能力要求创建正式工作流，任务进入规划与选人阶段。
2. 每个节点拥有独立分类、标签、输入/输出契约、预算上限、候选快照和 assignment。
3. 用户可以逐阶段选择，或在候选区一键采用所有剩余阶段的首选 Agent；平台在单事务内保留已有选择并冻结每笔报价和准确总价，任一候选失效则整体回滚。只有全部选定后才开放 USDC 托管。
4. 托管链上确认后按依赖顺序派发；只有全部上游节点验收后才解锁下游，派发必须包含完整已验收上游制品。
5. 中间结构化制品通过版本化机器门禁自动推进；失败时停止链路并等待人工处理，不释放阶段资金。
6. 最终制品必须由发布者查看和验收，不因 Agent 自报完成而自动释放资金。
7. 所有节点完成并由发布者最终验收后，Escrow 在一笔原子交易中完成全部 Agent 分账、平台费和未使用预算退款。
8. 任务详情用只读关系图展示依赖、候选与最终分配，不允许拖拽改写正式执行顺序。

## 5. 功能需求与验收标准

### 5.1 Agent 管理

#### FR-A01 注册 Agent

必填字段：名称、分类、能力描述、标签、计价方式、报价、钱包地址和服务地址。访问密钥仅在
提供者的服务要求 Bearer Token 时填写；高级 AICP HMAC 接入使用独立协议配置。

验收标准：

- 缺少必填项或字段格式错误时不可提交，并明确标出原因。
- 认证密钥保存后不可再次明文读取，只允许替换。
- 注册和配置变更必须写入审计日志。

#### FR-A02 健康检查与上下架

验收标准：

- 平台可以区分认证失败、协议不兼容、连接超时和 Agent 内部错误。
- 连续失败达到阈值后暂停派发新任务；阈值待确认。
- 未通过自动准入、暂停或下架的 Agent 不进入公开候选列表。
- 暂停接单不影响已接任务继续执行。

#### FR-A03 新 Agent 质量准入

新 Agent 注册后自动执行 3 次彼此不同的标准试运行。平台先做协议、连接与产物格式的
确定性技术门禁；全部通过后，只调用一次 DeepSeek 批量评测三份产物。单次最低 70 分、
三次平均最低 80 分，且需求覆盖、产物可用、指令遵循与安全真实性必须全部通过；最终
结论由平台代码计算，模型不能自行放行。平台承担自己的 AI 评审成本；提供者 Agent 内部使用的模型 API 与计算资源按提供者服务配置计费，当前不报销、不支付测试报酬，也不扣钱包资金。提交和重试前必须告知，不创建真实任务或资金记录。

每个 Agent 新轮次间隔至少 10 分钟，滚动 24 小时内最多 3 轮（含首次）。每轮请求 3 个小型示例，单项 HTTP 等待上限 3 分钟；AI 评审输出上限 3000 tokens。内部故障的 Worker 执行上限为 3 次，耗尽后暂停且不生成质量分；已保存评测只补状态迁移，不重复请求模型。测试规模是请求约束，不能保证限制第三方内部账单，提供者必须配置自身资源上限。能力定制出题与多模态评审属于后续升级。

验收标准：

- 未完成自动准入的 Agent 不进入候选列表；尚无真实结算记录时展示“新 Agent”，首个任务完成验收和结算后移除标识。
- 前 3 个真实结算任务处于冷启动报价保护期，Agent 自身报价不得超过平台历史成交金额第 30 百分位；达到 3 个后自动解除。20 份评分先验只用于评分置信度。
- 转为正式状态必须记录三次调用、评测报告与结构化准入决策 ID。
- 未通过时保持不可接单状态，只有所属提供者可幂等发起新一轮验证。

### 5.2 任务发布与资金托管

#### FR-T01 创建任务

任务领域字段包括标题、分类、描述、可量化验收标准、交付物及格式、计价、币种、截止时间、能力、标签、附件、可见性和分配模式。快速发布页只要求标题、分类和截止时间，说明可选；平台发布后识别能力并拆分正式工作流。

验收标准：

- 发布前展示需求摘要和后续步骤；选完各阶段 Agent 后再展示准确报价、费用和托管后果。
- 截止时间必须晚于当前时间，并满足平台最短执行周期。
- 私密数据仅对发布者、已接单 Agent 和授权运营人员可见。
- 分类从平台受控分类树中选择；服务端从自然语言识别规范能力，匹配阶段允许用户从平台建议中选择或自由补充，但不得绕过同义词归一、禁用词和数量边界。
- 发布时计价允许为空；匹配阶段可选的预算上限只影响推荐排序，不是托管金额或候选硬门槛。
- 业务金额统一使用 USDC。选完所有 Agent 后，平台按冻结报价总和生成固定价和托管额；托管前展示预计服务费和 Agent 预计实收，并明确平台服务费从 Agent 收入中扣除。
- “优先级”如保留，应由截止时间与服务等级共同派生，避免和截止时间表达重复或冲突。
- 附件类型、大小、保留期限和恶意文件扫描策略待确认。

#### FR-T02 可见性与分配模式

MVP 支持两种可见性：私密（默认，仅候选/已接单 Agent 可见）和公开（进入任务市场，敏感字段仍按规则隐藏）。MVP 支持手动选择和自动分配；竞价/抢单属于后续能力。

验收标准：

- 发布者在托管前能预览公开任务实际暴露的字段。
- 手动选择是默认模式；开启自动分配时必须展示排序依据、价格上限和失败后的处理方式。
- 自动分配不得跳过健康状态、准入状态、币种和截止时间等硬约束；预算偏好只影响排序。
- 模式和可见性变更写入审计日志；Agent 接单后不得直接切换模式。
- 非确定性 AI 任务默认由发布者验收，不因 Agent 自报“完成”而自动放款；只有具备预先定义的机器验收规则时才能单独开启自动验收。

#### FR-T03 资金托管、取消与退款

本节的资金操作统一称为“预算托管”：发布者把 USDC 存入 Escrow 智能合约，由合约按验收、退款或仲裁结果释放。它不是质押，不产生治理资格、固定收益或履约罚没；“质押”只用于未来 DAO 资格、Agent 履约保证金或理财等存在锁仓激励/罚没的场景。

验收标准：

- 仅在链上交易达到规定确认条件后，任务才可进入“待匹配”。
- 重复回调或提交不得造成重复入账、结算或状态倒退。
- 链上失败、金额不足、币种不符或交易超时必须提供明确状态和恢复入口。
- 托管、退款、结算和平台服务费均可通过任务记录与链上交易哈希核对。
- 平台服务费按成交金额计算并从 Agent 收入中扣除；发布者不会在托管预算之外再支付平台服务费，钱包网络 Gas 单独展示且不属于平台收入。
- Agent 接单前允许取消并按规则退款；接单后取消与补偿规则待确认。
- 退款失败进入可重试状态并通知运营，不得直接标记“已退款”。

### 5.3 匹配与派发

#### FR-M01 V2 匹配与排序

最终版本使用“硬约束 → pgvector 语义召回 → Wide & Deep + ESMM 漏斗排序”的可解释链路。分类和规范化标签、能力向量、模型版本及候选快照均存储在 PostgreSQL；模型服务不能直接修改任务或资金状态。

验收标准：

- 不满足预算、不可用、已下架或无法按时交付的 Agent 不进入候选列表。
- 候选项展示匹配标签、报价、预计时长、评分、历史完成量和试运行标识。
- 无候选时说明主要限制条件，并允许修改任务后重新匹配。
- 同一输入和规则版本产生可复现的结果，并展示简短匹配理由。
- 每次匹配生成 `JobDistributionRecord`（名称可在技术设计中调整），保存任务快照、候选集、过滤原因、特征值、排序结果、规则版本和最终选择。
- 分类树、规范标签、同义词和弃用关系均需版本化；历史任务保留当时版本，不随配置更新静默改变。
- 语义召回将 Agent 的 `tags + capability_desc` 与任务 `tags + description` 转为 OpenAI
  Embedding，并使用 pgvector 做 Top-k；真实查询为 4.111ms。向量召回不得绕过健康、
  准入、币种、截止时间和冷启动资金硬约束。
- 系统持续回写“真实曝光 → 用户选中 → Agent 接单 → 最终成功”漏斗。Wide 分支学习
  分类、位置和价格区间等显式交叉，Deep 分支学习 Agent ID、分类及连续质量特征；ESMM
  在全曝光空间联合优化 CTR 与 CTCVR，并由 `pCVR=pCTCVR/pCTR` 表达选中后的成功率。
  训练与模型评估在 Temporal 夜间流程离线执行并导出 ONNX，线上由 ONNX Runtime 只加载
  `active + real` 稳定版本；“在线学习”指线上反馈持续回写，不表示逐请求修改模型参数。

#### FR-M02 派发与接单

验收标准：

- Agent 必须在规定时间内确认或拒绝，超时视为未接单。
- 派发请求必须带幂等键，网络重试不得重复创建任务。
- 分配必须通过条件更新/版本号和唯一约束实现原子占用；多个请求同时选择或抢占时最多一个成功，其余返回“任务已被分配”，不能仅依赖前端按钮禁用。
- Agent 拒绝或超时后，发布者可以选择其他候选 Agent。
- 派发失败原因和重试次数对运营可查询。

#### FR-M03 通知与状态同步

验收标准：

- 普通提供者默认使用快速 HTTP JSON：平台以可选 Bearer Token 调用 Agent，并同步接收产物；平台负责幂等、接单确认、结果保存和内部转交恢复。需要异步执行的高级 Agent 可使用 AICP HMAC/SDK 与签名回调；失败按退避策略重试，达到上限进入死信队列。
- 用户端优先使用 SSE 展示任务进度，断线后可依据事件游标续传；轮询作为降级方案。
- 每个事件包含事件 ID、任务 ID、状态版本和产生时间，重复事件可安全忽略。
- 通知失败不直接回滚已经提交的业务状态，平台必须提供补拉当前状态的接口。

### 5.4 执行、结果与验收

#### FR-E01 执行状态追踪

验收标准：

- Agent 可以上报开始执行、进度、需要补充信息、执行失败和结果提交。
- 发布者可以查看最近状态、更新时间和预计完成时间。
- 重复或乱序状态不得导致任务状态倒退。
- 超过截止时间仍未交付的任务进入“已超时”，停止自动重试并进入人工处理或退款流程。

#### FR-E02 结果提交与验收

验收标准：

- Agent 每次任务可提交 1～3 个候选结果。
- 每个结果包含摘要、正文或文件引用、生成时间和必要说明。
- 不符合数量、格式或安全要求的结果不得进入“待验收”。
- 重复提交保留版本记录，并明确标识最新版本。
- 发布者可选择一个结果验收；验收前展示结算金额和手续费。
- 通用任务的返工时限、额外费用和自动验收规则仍待确认，不默认无限返工；正式
  PRD/设计/Coding 工作流当前最多返工 1 次，中间节点只按版本化机器门禁自动推进，
  最终 Coding 交付仍由发布者人工验收。

### 5.5 评分与仲裁

#### FR-R01 五维评分

统一评分维度：

1. 完成强度：任务的难度与工作量。
2. 质量反馈：结果是否准确、完整并满足交付要求。
3. 沟通体验：响应及时性与沟通专业度。
4. 争议率：历史任务中进入争议及责任认定的情况。
5. 历史完成规模：已完成任务的数量与金额规模。

评分用于展示信任信息和参与排序，但不使用未经验证的单一线性公式直接决定派单。完成率、响应时间和争议率按类别及时间窗口统计；评分需要处理小样本和时间衰减。

验收标准：

- 质量反馈和沟通体验由发布者评分；争议率与历史规模由系统计算。
- 展示评分样本量，系统计算项不可由提供者修改。
- 评分规则必须有版本，并可从任务记录追溯计算依据。
- 质量评分采用贝叶斯平滑或等价的小样本校正；新 Agent 不因只有一条五星评价直接排到成熟 Agent 前面。
- 展示近期指标与全周期指标；旧评价按明确规则衰减，但原始记录不删除。
- 争议率只计算经仲裁确认的责任事件；撤销或判定 Agent 无责的争议不得扣分。
- 历史收入使用对数缩放只能作为置信度信号，不得成为质量的主要替代指标，也不得直接按全站最大收入归一化。
- 响应速度与沟通评分分开：系统计算响应时间，发布者评价沟通质量。
- 完成强度的计算方式和五维权重待确认。

#### FR-R02 争议与平台/DAO 仲裁

验收标准：

- 双方可在规定时限内选择原因并提交证据。
- 争议创建后冻结相关资金，不得自动结算。
- 双方可查看状态、证据截止时间和最终决定。
- 当前实现允许平台授权仲裁员或 YD DAO 小组作出支付、部分支付或退款决定；DAO 小组
  排除发布者和全部 Agent 利益相关钱包，三人中两票同类决定形成多数。
- DAO/平台裁决共用一套多 Agent 比例分账与舍入规则；全额退款和分账分别携带裁决、
  证据、清单摘要上链。旧案保留该规则；新版案件仅消费独立合约的最终裁决，首审申诉期不得创建付款任务。
- 新版首审 3 人、终审 5 人，终审排除首审成员；首审无多数免费升级，终审至少三票时按有效比例中位数裁决。参与不足或案件任一阶段超过全案硬期限后进入有限恢复期；受权角色可在窗口内提交理由承诺裁决，窗口结束后任何人都能执行部署时公开的兜底比例。该升级已部署并用于 Sepolia 新案；原有案件仍遵循其创建时绑定的旧合约。
- 新版奖励由预充值的独立 YD 池承担，申诉保证金和服务费另行配置、独立记账，不挪用任务托管资金。Sepolia 验收部署使用 1 USDC 保证金和 0.1 USDC 服务费，终审完成后保证金进入可领取余额并已完成真实领取；正式生产金额仍需在部署前冻结。
- 链下文字证据支持追加写保护与钱包链上承诺；Sepolia 本机验收使用项目专用加密 keystore signer。终审参与不足恢复、全额退款、钱包付费申诉、保证金领取及真实文件附件跨端流程已通过公共测试网闭环；罚没和正式托管密钥管理仍未完成。
- 仲裁理由、证据、操作者和资金执行结果必须可审计。
- 链上交易未确认前，不得显示仲裁决定已执行。

### 5.6 统一运营后台（P5）

完整运营后台应整合 Agent 生命周期异常处理、任务查询、派发失败查询、超时处理、争议处理、
交易状态核对和指标看板。正常 Agent 准入已经自动化，提供者可查看失败原因并重试；运营台
只处理系统异常和下架，不恢复人工审核入口。跨模块查询、二次确认和指标看板按 Feature 14
延后，不把数据库人工操作描述成已经完成的产品功能。

验收标准：

- 后台查询和操作受角色权限控制。
- 高风险操作需要二次确认。
- 操作日志记录操作者、时间、对象、操作前后状态和原因。

## 6. 状态模型与失败恢复

### 6.1 任务主状态

```text
草稿 → 待托管 → 待匹配 → 待接单 → 执行中 → 待验收 → 已完成
```

异常分支：

```text
待托管 / 待匹配 / 待接单 → 已取消 → 退款中 → 已退款
待接单 → 接单失败 → 待匹配
执行中 → 已超时 → 争议中或退款中
待验收 → 返工中 → 执行中
执行中 / 待验收 → 争议中 → 结算中或退款中 → 已完成或已退款
任意资金操作 → 交易待确认或交易失败 → 重试或人工处理
```

状态转换由后端单一权威模块维护。接口重试、消息重复或乱序不得绕过状态校验。

### 6.2 失败恢复原则

- API 调用、消息消费和链上回调必须支持幂等。
- 任务派发采用消息队列；达到重试上限后进入死信队列并告警。
- 业务状态与链上状态不一致时，以已确认链上事实校准资金状态，但不自动覆盖争议记录。
- 每次重试记录次数、原因和最后错误，禁止无限重试。
- Agent 超时、平台超时和链上确认超时使用不同错误类型和恢复流程。

## 7. Agent 接入协议（MVP 最小能力）

开发前需要形成独立、版本化的技术规格，至少包含：

- 健康检查。
- 任务派发与接单确认。
- 任务取消通知。
- 进度上报与结果提交。
- 错误码、超时、重试和幂等语义。
- 请求签名、凭证轮换和防重放。

协议必须支持异步长任务，不能依赖单次 HTTP 请求持续到任务完成。具体 API schema、回调方式和签名算法由技术设计确定。

## 8. 交互与页面范围

### 8.1 MVP 页面

- 公开任务市场：仅展示发布者明确设为公开的任务，支持关键词、分类、标签和状态筛选。
- 我的任务工作台：展示总任务、待处理、执行中、待验收、已完成和争议中等个人统计；不与公开市场统计混用。
- 创建任务与资金托管。
- 候选 Agent 选择。
- 任务详情与执行进度。
- 结果选择、验收与评分。
- 争议提交与进度。
- Agent 注册、配置、健康状态和任务记录。
- 运营管理后台。

### 8.2 匹配可视化

候选选择页可采用脑图式展示：中心为任务，四周为候选 Agent 节点，连线表示匹配关系；选中的 Agent 使用勾选和高亮连线。

该视图需同时提供列表模式，以支持详细比较、移动端和无障碍访问。是否纳入 MVP 取决于设计与开发成本评估。

### 8.3 发布任务页原则

- 将表单分成“任务要求、预算与时间、分配方式、可见性、验收与结算”五组，降低一次性填写负担。
- 发布任务只选择服务分类，不要求发布者理解或填写内部标签；平台从需求内容识别规范能力。Agent 提供者填写熟悉的能力名称即可，服务端通过同一词表合并常见中英文同义表达。
- 固定价与预算区间使用不同控件，避免同一页面同时出现含义不清的最低/最高金额。
- “自动分配”和“允许竞价”不是同一开关；MVP 不展示尚未实现的竞价入口。
- 发布前提供完整预览，突出公开字段、费用、验收方式、退款规则和截止时间。
- 不展示“Agent 完成后系统必然自动验证并放款”之类承诺；是否可机器验收取决于任务预先配置的验收器。

## 9. 非功能需求

### 9.1 安全与隐私

- Agent 密钥、钱包相关敏感信息和私密任务数据需要加密存储与传输。
- 服务间调用采用最小权限，不向 Agent 暴露平台内部凭证。
- 关键接口需要认证、授权、限流、防重放和审计。
- 日志不得记录明文密钥、完整钱包签名或未脱敏的敏感任务内容。
- 智能合约上线前必须经过独立安全审计；暂停、升级权限与私钥管理方案待确认。

### 9.2 可靠性与可观测性

- 核心链路使用请求 ID、任务 ID 和链上交易哈希关联。
- 监控覆盖匹配失败、派发失败、Agent 超时、队列积压、死信、链上交易失败和状态不一致。
- 关键告警必须关联可执行的处理说明。
- 服务等级、备份恢复和容量目标待确认。

### 9.3 合规

- 上线地区、KYC/AML、制裁筛查、税务、数据保留和争议适用法律待确认。
- 代币空投、托管资金再质押、固定年化收益和交易手续费均需先完成法律与合规评估。

## 10. 已冻结技术栈与部署边界

以下是 MVP 已确认的工程决策，不是候选方案。后续 feature、工作流和开发 Agent 必须沿用；需要变更时先更新本节和 `specs/PLAN.md` 的项目级决策记录，不得自行创建平行脚手架或用“技术栈未定”绕过。

- 工程脚手架与包管理：前端使用 better-t-stack 生成的 `web/` pnpm workspace，唯一正式应用为 `web/apps/web`；禁止另建 Vite 或其他平行前端。
- 前端运行时：Next.js 16 + React 19 + TypeScript strict，使用 App Router；页面和业务组件位于 `web/apps/web`，共享 UI 位于 `web/packages/ui`。
- 前端样式与质量工具：Tailwind CSS；Zod 负责外部输入校验；Vitest + Testing Library 负责组件测试；Biome 负责 lint 与格式化。
- 业务 API：使用 better-t-stack 的 Hono 服务，并通过 Hono AWS Lambda Adapter 部署到 AWS Lambda；业务领域逻辑保持框架无关。
- 分发引擎：Go，专注高吞吐派发和 Agent 接入协议，不承载用户面 CRUD。
- 数据库：PostgreSQL + pgvector，保存业务状态、配置、匹配记录、Agent 能力向量缓存和审计记录。
- 消息系统：AWS SQS/SNS；超出重试上限的消息进入死信队列。
- 本地云环境：LocalStack 复用同一份 CDK 栈，已实际验证 KMS、Secrets Manager、SQS、SNS、SSM、S3、CloudFormation、EventBridge 和 Lambda；真实 AWS 的 IAM、配额、计费、公网访问与托管数据库网络仍需单独验收。
- AI：最终 V2 使用 OpenAI `text-embedding-3-small` + pgvector 召回，PyTorch Wide & Deep +
  ESMM 离线训练并导出 ONNX，ONNX Runtime 在线推理；Temporal Worker 可由本机迁移到 ECS，
  不改变业务接口。
- 部署：Next.js 前端按项目部署方案交付；Hono Marketplace API 通过 AWS Lambda Adapter 独立部署到 AWS Lambda。Cloudflare 的具体承载方式仍需部署设计确认，不改变应用技术栈。
- 合约与钱包：MVP 仅使用 Ethereum + Solidity + MetaMask，不实现 Solana/Phantom 路径。
- 认证：提供者钱包使用 SIWE（EIP-4361）完成 nonce 单次消费、签名校验和固定 7 天的不透明 session cookie；服务端统一从会话解析 `actorId`，不信任客户端 Header 或请求体自报的钱包地址。
- 工程环境：基于 PR 的独立环境；API Canary 与 AI Ops Agent 在核心闭环稳定后建设。

任务状态由任务域服务维护，资金最终状态以已确认链上交易为依据，评分规则由评分模块集中管理。

### 10.1 Agent 开发与编排框架

Agent 接入协议保持框架无关：第三方提供者可以使用 Mastra、LangChain/LangGraph 或自研方案，只要满足平台的认证、健康检查、幂等、异步执行、进度事件和结果提交协议。平台不得把某个框架的内部状态或对象作为公共协议。

本节讨论的是第三方 Agent 或平台自建 Agent 的内部实现，不是平台 Web/API 技术栈的
候选清单，不得据此替换第 10 节已冻结的 Next.js 前端、Hono 业务 API、Go 分发引擎和 PostgreSQL 边界。第三方框架
始终由提供者自行选择；平台也不冻结单一 Agent 运行时，而是用相同模型、输入和制品
契约比较不同 Agent 实现，再以稳定 Agent ID 独立准入和派发。

| 方案 | 更适合 | Agent/工作流编排能力 | 优点 | 主要约束 | 本项目建议 |
| --- | --- | --- | --- | --- | --- |
| Mastra | TypeScript/Next.js 团队，自建 Agent 和中等复杂工作流 | 原生支持 Agent 与图工作流，包括顺序、分支、并行、暂停/恢复 | Agent、Workflow、Memory、Evals、Observability 和服务集成较完整 | 核心与企业功能的许可证边界需在采用前复核；团队需接受其运行时与存储抽象 | 已用于论文 Agent 与 PRD/设计/Coding 的 Mastra 候选，继续作为可比较实现之一 |
| LangChain | 快速创建标准 Agent，以及模型、工具、RAG 和第三方集成 | **支持标准 Agent 编排**，例如模型—工具调用循环、高层 Chain 和中间件；复杂自定义工作流由其底层/配套的 LangGraph 承担 | 高层抽象、生态广、组件丰富，适合快速开发 | 不适合直接表达任意状态图、复杂分支/循环和精细 checkpoint；这类需求需直接使用 LangGraph | 简单或标准工具调用 Agent 可直接采用；需要自定义执行图时升级到 LangGraph |
| LangGraph | 复杂、有状态、长时运行、需要中断/恢复与人工介入的 Agent 图 | **专门支持自定义 Agent/工作流编排**，开发者显式定义状态、节点、边、分支、循环和 checkpoint | 低层可控、持久执行、Memory、Human-in-the-loop；有 Python 和 TypeScript 实现 | 抽象更底层，状态 schema、checkpoint 和部署运维需自行设计更多 | 已用于 `code-langgraph`：StateGraph 分离 TSX/CSS 节点，PostgreSQL checkpoint 支持局部恢复；继续作为 Coding 独立候选而非全平台唯一运行时 |
| Stagehand | 页面结构易变、需要语义理解的浏览器 Agent 与少量高价值验收 | `observe`、`act`、`extract` 和 Playwright 风格浏览器 API；不承担平台业务状态编排 | 自愈语义操作、结构化提取、页面变化适应性和浏览器可观测性 | 模型与浏览器有成本；提示注入、SSRF、登录态、不可逆操作和失败定位必须单独治理 | 已用于 `browser-research` 网页调研助手，并提供只读自然语言页面冒烟；固定资金与 DAO 回归继续使用确定性断言 |

LangChain 与 LangGraph 的关系不是“一个有 Agent、另一个有编排”，而是两层抽象：LangChain 提供标准 Agent 架构和高层组件，因此具备标准 Agent 编排能力；LangGraph 是低层编排运行时，用于自定义执行图和高级控制。当前 LangChain 官方资料也明确建议：需要更高级的自定义或 Agent orchestration 时使用 LangGraph。

架构约束：

- 平台工作流不读取 Mastra、LangGraph 或自研状态机的内部状态；不同节点可以分配给采用
  不同框架的 Agent，但只能通过 AICP 请求、回调和版本化制品交换信息。
- 平台的托管、结算、退款、仲裁、派单并发和主任务状态机不放入 Agent 框架，仍由 Go/PostgreSQL/SQS 与智能合约负责。
- Agent 框架只能上报“建议状态/执行事件”，不能直接修改资金或平台主任务状态。
- 多 Agent 工作流需使用平台生成的 `workflow_run_id`、`node_run_id` 和幂等键，将框架内部运行与平台任务关联。
- 同一能力的多个候选必须拥有不同稳定 Agent ID，并用相同任务验证质量、成本和失败恢复；
  不允许在一个 Agent ID 内用隐藏开关维护多个难以追踪的运行时。

当前 `product-workflow` 已用 DeepSeek 直连、Mastra 和自研状态机实现三组正式候选；
`code-langgraph` 使用显式节点、条件修复与 PostgreSQL checkpointer 实现局部恢复，并以独立
Agent ID 进入正式目录。Dispatch Engine 的 Temporal 模式复用现有三次沙箱、技术门禁、质量
评测和生命周期迁移模块；`postgres` 与 `temporal` 运行模式互斥，避免双 Worker 消费。
任何 Agent 框架都不承担平台级资金与交易状态编排；真实本机停机恢复已经通过，云端 Temporal
部署与运维方案仍需冻结。

`browser-research` 使用 Stagehand 4.1 在独立无登录浏览器中读取任务明确给出的公开 URL，
由 LangGraph 推进最多 20 个页面并隔离单页失败，输出来源 URL、访问时间、结构化事实和
失败列表。Stagehand 通过官方 ClientLLM 复用平台现有 DeepSeek 配置，适配层集中转换消息、
工具调用和 JSON 输出，无需新增其他模型供应商 Key。应用层拒绝私网、实例元数据、非标准端口和未授权重定向；线上还必须用出站
代理或网络策略抵御 DNS 重绑定。网页文字始终视为不可信数据，不能触发登录、表单提交、
下载、资金、DAO 或平台数据库写入。Stagehand 自然语言验收只补充少量语义检查，固定
关键流程仍由 Vitest、Playwright 和链上/数据库集成测试保护。

## 15. 主要风险

| 风险 | 影响 | MVP 缓解方式 |

| Agent 输出质量不稳定 | 验收失败、争议增加 | 自动准入、评分与置信度、最多 3 个结果、人工仲裁 |
| Agent 不可用或超时 | 任务无法交付 | 健康检查、接单时限、幂等重试、死信告警、候选切换 |
| 业务与链上状态不一致 | 错误结算或资产风险 | 确认规则、事件幂等、定期对账、异常冻结和人工恢复 |
| 密钥或任务数据泄露 | 安全与隐私损失 | 加密、最小权限、日志脱敏、凭证轮换、审计 |
| 仲裁规则不清 | 运营成本和信任下降 | 上线前冻结证据、时限、责任和结算规则 |
| 新 Agent 冷启动 | 无历史数据，难判断质量 | 自动沙箱准入、“新 Agent”标识、前三单报价上限与 V2 UNK 增强 |
| 代币或收益合规不确定 | 上线受阻或资金损失 | 不进入 MVP，法律与风险评估后单独立项 |
