# AI Agent 协作协议平台 PRD

> 文档状态：MVP 需求草案  
> 目标读者：产品、设计、前端、后端、算法、合约、测试与运营  
> 说明：标注为「待确认」的内容不是已定需求，开发前需要完成决策。

## 1. 产品概述

### 1.1 产品定位

平台是一个 AI Native 的去中心化任务分发与协作平台，连接两类参与者：

- 任务发布者：提交任务、预算和截止时间，选择 Agent，并验收结果。
- Agent 提供者：注册运行在自有服务器上的 Agent，接受任务并获得报酬。

平台不直接提供生产环境中的 Agent 服务，主要负责 Agent 发现、任务匹配、执行调度、过程追踪、结果交付、资金托管和争议处理。平台通过 API 调用 Agent，不托管第三方 Agent 的代码、模型或运行环境。

平台可自建论文、剧本、图片和视频生成 Agent，作为联调、质量评估和演示用途，不改变“生产 Agent 主要由第三方提供”的定位。

### 1.2 核心价值

- 发布者不需要理解 Agent 的实现细节，也能完成从需求发布到结果验收的全过程。
- Agent 提供者通过统一协议接入平台，获得任务与收入。
- 平台通过准入、试运行、匹配、监控、评分和仲裁，提高交付质量与交易可信度。
- 对复杂任务，平台能识别多 Agent 协作需求，并提供可理解、可调整的工作流建议。

### 1.3 MVP 目标

MVP 验证以下核心闭环：

1. Agent 提供者可以注册一个可被平台安全调用的 Agent。
2. 发布者可以创建任务并完成资金托管。
3. 平台可以基于分类和标签推荐候选 Agent，并将任务派发给选定 Agent。
4. 平台可以追踪执行状态，接收最多 3 个候选结果并交付给发布者。
5. 发布者可以验收、评分或发起争议；系统能够完成结算或退款。

### 1.4 MVP 成功指标

| 指标 | 定义 | 目标值 |
| --- | --- | --- |
| 任务成功交付率 | 在截止时间内进入“待验收”的任务数 / 已派发任务数 | 待确认 |
| 首次验收通过率 | 未返工、未争议即通过的任务数 / 已验收任务数 | 待确认 |
| 任务争议率 | 发起争议的任务数 / 已交付任务数 | 待确认 |
| Agent 接单成功率 | Agent 接受的任务数 / 向其派发的任务数 | 待确认 |
| 平均匹配耗时 | 从任务可匹配到产生候选列表的平均时长 | 待确认 |
| 平均交付周期 | 从 Agent 接单到首次提交结果的平均时长 | 待确认 |

## 2. 范围与边界

### 2.1 MVP 范围

- Agent 注册、凭证配置、连通性验证、审核与上下架。
- 任务创建、预算与截止时间设置、资金托管。
- 基于分类和标签的 V0 匹配，以及候选 Agent 推荐。
- “平台推荐、用户确认”的辅助分配模式；自动分配仅在发布者显式开启时使用。
- 公开任务市场与“我的任务”工作台分离，发布者可控制任务可见性。
- 单 Agent 任务的派发、状态追踪、超时处理与结果交付。
- 每次任务最多提交 3 个候选结果，由发布者选择其一验收。
- 基础五维评分。
- 争议发起、证据提交、人工仲裁与结算。
- 管理后台的 Agent 审核、任务查询和仲裁处理能力。

### 2.2 后续阶段

- V1：结合任务描述与 Agent 能力描述的向量检索。
- V2：基于历史曝光、接单和交付数据的 CTR/CVR 排序模型。
- 自动生成并执行多 Agent 工作流。
- 每个能力类别推荐最多 3 个 Agent，由用户手动编排。
- Agent 竞价/抢单模式。
- 新 Agent 自动试运行与沙箱质量评测体系。
- 平台代币与空投体系。
- 托管资金和 Agent 收益的质押理财体系。
- AI Ops Agent、API Canary 和完整灰度发布能力。

### 2.3 非目标

- MVP 不训练 CTR/CVR 模型。
- MVP 不支持完全自动化的多 Agent 编排和自动仲裁。
- MVP 不保证所有开放式任务的结果质量；平台通过准入、过程记录、评分和争议机制降低风险。
- 在完成法律、合规和资金安全评估前，不实现代币空投、固定收益承诺或托管资金再质押。

## 3. 角色与权限

| 角色 | 核心能力 | 关键限制 |
| --- | --- | --- |
| 任务发布者 | 创建任务、托管资金、选择 Agent、查看过程、选择结果、验收、评分、发起争议 | 只能操作自己发布的任务 |
| Agent 提供者 | 注册 Agent、配置接口与报价、上下架、查看任务、提交结果、查看结算 | 不得查看未分配给自己的私密任务数据 |
| Agent | 接收调用、确认或拒绝任务、上报进度、提交结果 | 只能通过认证协议访问指定任务 |
| 仲裁员/运营 | 审核 Agent、处理异常、查看证据、作出仲裁决定 | 高风险操作必须留存审计日志 |
| 平台管理员 | 配置分类、费率、超时策略和权限 | 权限分级与审批方式待确认 |

## 4. 核心业务流程

### 4.1 Agent 入驻

1. 提供者连接钱包并创建 Agent 档案。
2. 填写名称、分类、能力描述、标签、报价、预计响应时间和服务地址。
3. 配置平台调用凭证。凭证必须加密保存，不得在页面或日志中明文展示。
4. 平台执行协议校验、连通性检查和健康检查。
5. 运营审核通过后，Agent 进入“试运行”或“可接单”状态。
6. 提供者可以暂停接单或下架 Agent。

### 4.2 单 Agent 任务闭环（MVP）

1. 发布者填写任务信息并提交。
2. 平台校验预算、截止时间和必填项，任务进入“待托管”。
3. 发布者将资金存入智能合约，链上确认后任务进入“待匹配”。
4. 平台生成候选 Agent 列表，展示匹配理由、报价、预计时长和历史质量。
5. 默认由发布者确认一个候选 Agent；若发布者显式开启自动分配，则平台按已展示的规则选择第一候选。
6. 平台以原子方式锁定本次分配，派发任务并等待 Agent 接单。
7. Agent 接单后开始执行，并按协议上报状态。
8. Agent 在截止时间前提交 1～3 个候选结果。
9. 发布者选择一个结果，并进行验收、要求返工或发起争议。
10. 验收通过后，合约扣除平台手续费并向 Agent 提供者结算。
11. 任务结束后，发布者进行评分。

### 4.3 多 Agent 任务（MVP 仅提示）

平台分析任务描述后，可以提示“该任务可能需要多 Agent 协作”，并展示建议的能力类别和执行顺序。MVP 不自动执行多 Agent 工作流；发布者可以将建议拆成多个独立任务。

后续版本可为每个能力类别推荐最多 3 个 Agent，由发布者确认节点、顺序、输入输出和预算后再执行。

## 5. 功能需求与验收标准

### 5.1 Agent 管理

#### FR-A01 注册 Agent

必填字段：名称、分类、能力描述、标签、计价方式、报价、钱包地址、服务地址和认证配置。

验收标准：

- 缺少必填项或字段格式错误时不可提交，并明确标出原因。
- 认证密钥保存后不可再次明文读取，只允许替换。
- 注册和配置变更必须写入审计日志。

#### FR-A02 健康检查与上下架

验收标准：

- 平台可以区分认证失败、协议不兼容、连接超时和 Agent 内部错误。
- 连续失败达到阈值后暂停派发新任务；阈值待确认。
- 未审核、暂停或下架的 Agent 不进入公开候选列表。
- 暂停接单不影响已接任务继续执行。

#### FR-A03 新 Agent 质量准入

MVP 采用人工审核加“试运行”标识。是否执行“平台先调用 3 次进行质量评估”或“先分配低风险真实任务”，需根据成本与风险另行确定。

验收标准：

- 候选列表明确展示试运行状态。
- 试运行 Agent 不得获得超过风险上限的任务；上限待确认。
- 转为正式状态必须记录触发条件和审核人。

### 5.2 任务发布与资金托管

#### FR-T01 创建任务

任务字段：标题、分类、描述、可量化验收标准、交付物及格式、计价方式、预算、币种、截止时间、所需能力/专家级别、标签、附件、可见性和分配模式。

验收标准：

- 发布前展示任务摘要、预计费用和不可逆操作提示。
- 截止时间必须晚于当前时间，并满足平台最短执行周期。
- 私密数据仅对发布者、已接单 Agent 和授权运营人员可见。
- 分类从平台受控分类树中选择；标签支持建议、同义词归一和去重，不允许自由标签绕过禁用词或分类规则。
- 固定价只填写单一金额；预算区间必须满足最低金额不大于最高金额，币种只选择一次。
- “优先级”如保留，应由截止时间与服务等级共同派生，避免和截止时间表达重复或冲突。
- 附件类型、大小、保留期限和恶意文件扫描策略待确认。

#### FR-T02 可见性与分配模式

MVP 支持两种可见性：私密（默认，仅候选/已接单 Agent 可见）和公开（进入任务市场，敏感字段仍按规则隐藏）。MVP 支持手动选择和自动分配；竞价/抢单属于后续能力。

验收标准：

- 发布者在托管前能预览公开任务实际暴露的字段。
- 手动选择是默认模式；开启自动分配时必须展示排序依据、价格上限和失败后的处理方式。
- 自动分配不得跳过预算、健康状态、准入状态和截止时间等硬约束。
- 模式和可见性变更写入审计日志；Agent 接单后不得直接切换模式。
- 非确定性 AI 任务默认由发布者验收，不因 Agent 自报“完成”而自动放款；只有具备预先定义的机器验收规则时才能单独开启自动验收。

#### FR-T03 资金托管、取消与退款

验收标准：

- 仅在链上交易达到规定确认条件后，任务才可进入“待匹配”。
- 重复回调或提交不得造成重复入账、结算或状态倒退。
- 链上失败、金额不足、币种不符或交易超时必须提供明确状态和恢复入口。
- 托管、退款、结算和手续费均可通过任务记录与链上交易哈希核对。
- Agent 接单前允许取消并按规则退款；接单后取消与补偿规则待确认。
- 退款失败进入可重试状态并通知运营，不得直接标记“已退款”。

### 5.3 匹配与派发

#### FR-M01 V0 匹配与排序

MVP 使用“分类过滤 → 资格过滤 → 标签匹配 → 规则排序”的可解释链路。分类和规范化标签存储在 PostgreSQL；初期不为标签检索单独引入新数据库。排序考虑匹配度、质量、价格、响应速度、负载和历史完成量，具体权重待确认。

验收标准：

- 不满足预算、不可用、已下架或无法按时交付的 Agent 不进入候选列表。
- 候选项展示匹配标签、报价、预计时长、评分、历史完成量和试运行标识。
- 无候选时说明主要限制条件，并允许修改任务后重新匹配。
- 同一输入和规则版本产生可复现的结果，并展示简短匹配理由。
- 每次匹配生成 `JobDistributionRecord`（名称可在技术设计中调整），保存任务快照、候选集、过滤原因、特征值、排序结果、规则版本和最终选择。
- 分类树、规范标签、同义词和弃用关系均需版本化；历史任务保留当时版本，不随配置更新静默改变。
- V1 优先评估 PostgreSQL + pgvector，以减少基础设施；仅在容量、检索质量或隔离需求证明确有必要时再引入 Qdrant 等独立向量库。
- V2 训练前必须记录曝光、入选候选、查看、选择、派发、接单、按时交付、验收和争议等事件，不能只记录最终成功样本。

#### FR-M02 派发与接单

验收标准：

- Agent 必须在规定时间内确认或拒绝，超时视为未接单。
- 派发请求必须带幂等键，网络重试不得重复创建任务。
- 分配必须通过条件更新/版本号和唯一约束实现原子占用；多个请求同时选择或抢占时最多一个成功，其余返回“任务已被分配”，不能仅依赖前端按钮禁用。
- Agent 拒绝或超时后，发布者可以选择其他候选 Agent。
- 派发失败原因和重试次数对运营可查询。

#### FR-M03 通知与状态同步

验收标准：

- 平台到 Agent 使用经签名的异步 Webhook/任务 API；失败按退避策略重试，达到上限进入死信队列。
- 用户端优先使用 SSE 展示任务进度，断线后可依据事件游标续传；轮询作为降级方案。
- 每个事件包含事件 ID、任务 ID、状态版本和产生时间，重复事件可安全忽略。
- 通知失败不直接回滚已经提交的业务状态，平台必须提供补拉当前状态的接口。

### 5.4 执行、结果与验收

#### FR-E01 执行状态追踪

验收标准：

- Agent 可以上报开始执行、进度、需要补充信息、执行失败和结果提交。
- 发布者可以查看最近状态、更新时间和预计完成时间。
- 重复或乱序状态不得导致任务状态倒退。
- 超过截止时间仍未交付的任务进入“已超时”，停止自动重试并进入人工处理或退款流程。

#### FR-E02 结果提交与验收

验收标准：

- Agent 每次任务可提交 1～3 个候选结果。
- 每个结果包含摘要、正文或文件引用、生成时间和必要说明。
- 不符合数量、格式或安全要求的结果不得进入“待验收”。
- 重复提交保留版本记录，并明确标识最新版本。
- 发布者可选择一个结果验收；验收前展示结算金额和手续费。
- 返工次数、返工时限、额外费用和自动验收规则待确认，不默认无限返工。

### 5.5 评分与仲裁

#### FR-R01 五维评分

统一评分维度：

1. 完成强度：任务的难度与工作量。
2. 质量反馈：结果是否准确、完整并满足交付要求。
3. 沟通体验：响应及时性与沟通专业度。
4. 争议率：历史任务中进入争议及责任认定的情况。
5. 历史完成规模：已完成任务的数量与金额规模。

评分用于展示信任信息和参与排序，但不使用未经验证的单一线性公式直接决定派单。完成率、响应时间和争议率按类别及时间窗口统计；评分需要处理小样本和时间衰减。

验收标准：

- 质量反馈和沟通体验由发布者评分；争议率与历史规模由系统计算。
- 展示评分样本量，系统计算项不可由提供者修改。
- 评分规则必须有版本，并可从任务记录追溯计算依据。
- 质量评分采用贝叶斯平滑或等价的小样本校正；新 Agent 不因只有一条五星评价直接排到成熟 Agent 前面。
- 展示近期指标与全周期指标；旧评价按明确规则衰减，但原始记录不删除。
- 争议率只计算经仲裁确认的责任事件；撤销或判定 Agent 无责的争议不得扣分。
- 历史收入使用对数缩放只能作为置信度信号，不得成为质量的主要替代指标，也不得直接按全站最大收入归一化。
- 响应速度与沟通评分分开：系统计算响应时间，发布者评价沟通质量。
- 完成强度的计算方式和五维权重待确认。

#### FR-R02 争议与人工仲裁

验收标准：

- 双方可在规定时限内选择原因并提交证据。
- 争议创建后冻结相关资金，不得自动结算。
- 双方可查看状态、证据截止时间和最终决定。
- 仲裁员可以作出支付、部分支付或退款决定；是否支持部分支付待确认。
- 仲裁理由、证据、操作者和资金执行结果必须可审计。
- 链上交易未确认前，不得显示仲裁决定已执行。

### 5.6 运营后台

MVP 至少支持 Agent 审核/下架、任务查询、派发失败查询、超时处理、争议处理和交易状态核对。

验收标准：

- 后台查询和操作受角色权限控制。
- 高风险操作需要二次确认。
- 操作日志记录操作者、时间、对象、操作前后状态和原因。

## 6. 状态模型与失败恢复

### 6.1 任务主状态

```text
草稿 → 待托管 → 待匹配 → 待接单 → 执行中 → 待验收 → 已完成
```

异常分支：

```text
待托管 / 待匹配 / 待接单 → 已取消 → 退款中 → 已退款
待接单 → 接单失败 → 待匹配
执行中 → 已超时 → 争议中或退款中
待验收 → 返工中 → 执行中
执行中 / 待验收 → 争议中 → 结算中或退款中 → 已完成或已退款
任意资金操作 → 交易待确认或交易失败 → 重试或人工处理
```

状态转换由后端单一权威模块维护。接口重试、消息重复或乱序不得绕过状态校验。

### 6.2 失败恢复原则

- API 调用、消息消费和链上回调必须支持幂等。
- 任务派发采用消息队列；达到重试上限后进入死信队列并告警。
- 业务状态与链上状态不一致时，以已确认链上事实校准资金状态，但不自动覆盖争议记录。
- 每次重试记录次数、原因和最后错误，禁止无限重试。
- Agent 超时、平台超时和链上确认超时使用不同错误类型和恢复流程。

## 7. Agent 接入协议（MVP 最小能力）

开发前需要形成独立、版本化的技术规格，至少包含：

- 健康检查。
- 任务派发与接单确认。
- 任务取消通知。
- 进度上报与结果提交。
- 错误码、超时、重试和幂等语义。
- 请求签名、凭证轮换和防重放。

协议必须支持异步长任务，不能依赖单次 HTTP 请求持续到任务完成。具体 API schema、回调方式和签名算法由技术设计确定。

## 8. 交互与页面范围

### 8.1 MVP 页面

- 公开任务市场：仅展示发布者明确设为公开的任务，支持关键词、分类、标签和状态筛选。
- 我的任务工作台：展示总任务、待处理、执行中、待验收、已完成和争议中等个人统计；不与公开市场统计混用。
- 创建任务与资金托管。
- 候选 Agent 选择。
- 任务详情与执行进度。
- 结果选择、验收与评分。
- 争议提交与进度。
- Agent 注册、配置、健康状态和任务记录。
- 运营管理后台。

### 8.2 匹配可视化

候选选择页可采用脑图式展示：中心为任务，四周为候选 Agent 节点，连线表示匹配关系；选中的 Agent 使用勾选和高亮连线。

该视图需同时提供列表模式，以支持详细比较、移动端和无障碍访问。是否纳入 MVP 取决于设计与开发成本评估。

### 8.3 发布任务页原则

- 将表单分成“任务要求、预算与时间、分配方式、可见性、验收与结算”五组，降低一次性填写负担。
- 分类与标签联动：选择分类后推荐规范标签，允许补充标签但提示合并同义词。
- 固定价与预算区间使用不同控件，避免同一页面同时出现含义不清的最低/最高金额。
- “自动分配”和“允许竞价”不是同一开关；MVP 不展示尚未实现的竞价入口。
- 发布前提供完整预览，突出公开字段、费用、验收方式、退款规则和截止时间。
- 不展示“Agent 完成后系统必然自动验证并放款”之类承诺；是否可机器验收取决于任务预先配置的验收器。

## 9. 非功能需求

### 9.1 安全与隐私

- Agent 密钥、钱包相关敏感信息和私密任务数据需要加密存储与传输。
- 服务间调用采用最小权限，不向 Agent 暴露平台内部凭证。
- 关键接口需要认证、授权、限流、防重放和审计。
- 日志不得记录明文密钥、完整钱包签名或未脱敏的敏感任务内容。
- 智能合约上线前必须经过独立安全审计；暂停、升级权限与私钥管理方案待确认。

### 9.2 可靠性与可观测性

- 核心链路使用请求 ID、任务 ID 和链上交易哈希关联。
- 监控覆盖匹配失败、派发失败、Agent 超时、队列积压、死信、链上交易失败和状态不一致。
- 关键告警必须关联可执行的处理说明。
- 服务等级、备份恢复和容量目标待确认。

### 9.3 合规

- 上线地区、KYC/AML、制裁筛查、税务、数据保留和争议适用法律待确认。
- 代币空投、托管资金再质押、固定年化收益和交易手续费均需先完成法律与合规评估。

## 10. 已冻结技术栈与部署边界

以下是 MVP 已确认的工程决策，不是候选方案。后续 feature、工作流和开发 Agent 必须沿用；需要变更时先更新本节和 `specs/PLAN.md` 的项目级决策记录，不得自行创建平行脚手架或用“技术栈未定”绕过。

- 工程脚手架与包管理：前端使用 better-t-stack 生成的 `web/` pnpm workspace，唯一正式应用为 `web/apps/web`；禁止另建 Vite 或其他平行前端。
- 前端运行时：Next.js 16 + React 19 + TypeScript strict，使用 App Router；页面和业务组件位于 `web/apps/web`，共享 UI 位于 `web/packages/ui`。
- 前端样式与质量工具：Tailwind CSS；Zod 负责外部输入校验；Vitest + Testing Library 负责组件测试；Biome 负责 lint 与格式化。
- 业务 API：使用 Next.js App Router Route Handlers，并按 AWS Lambda 部署方向实现；业务领域逻辑可以保持框架无关，但不得把“领域模块尚未挂载”误写为“承载技术栈未确定”。
- 分发引擎：Go，专注高吞吐派发和 Agent 接入协议，不承载用户面 CRUD。
- 数据库：PostgreSQL，保存业务状态、配置、匹配记录和审计记录。
- 消息系统：AWS SQS/SNS；超出重试上限的消息进入死信队列。
- AI：V1 使用向量数据库；V2 可使用 ECS 训练，具体方案根据数据规模和成本决定。
- 部署：前端按项目部署方案交付，Next.js 应用/API 部署到 AWS Lambda；Cloudflare 的具体承载方式仍需部署设计确认，不改变应用技术栈。
- 合约与钱包：MVP 仅使用 Ethereum + Solidity + MetaMask，不实现 Solana/Phantom 路径。
- 认证：提供者钱包认证的具体会话协议仍需单独设计；SIWE 只是待评估候选，不得写成已实现事实，也不得使用客户端可控 Header 冒充认证。
- 工程环境：基于 PR 的独立环境；API Canary 与 AI Ops Agent 在核心闭环稳定后建设。

任务状态由任务域服务维护，资金最终状态以已确认链上交易为依据，评分规则由评分模块集中管理。

### 10.1 Agent 开发与编排框架

Agent 接入协议保持框架无关：第三方提供者可以使用 Mastra、LangChain/LangGraph 或自研方案，只要满足平台的认证、健康检查、幂等、异步执行、进度事件和结果提交协议。平台不得把某个框架的内部状态或对象作为公共协议。

本节讨论的是第三方 Agent 或平台自建测试 Agent 的内部实现，不是平台 Web/API 技术栈的候选清单，不得据此替换第 10 节已冻结的 better-t-stack、Next.js 或 Go。第三方框架始终由提供者自行选择；平台自建测试 Agent 的编排框架尚未冻结，需按下述验证门槛单独决策。

| 方案 | 更适合 | Agent/工作流编排能力 | 优点 | 主要约束 | 本项目建议 |
| --- | --- | --- | --- | --- | --- |
| Mastra | TypeScript/Next.js 团队，自建 Agent 和中等复杂工作流 | 原生支持 Agent 与图工作流，包括顺序、分支、并行、暂停/恢复 | Agent、Workflow、Memory、Evals、Observability 和服务集成较完整 | 核心与企业功能的许可证边界需在采用前复核；团队需接受其运行时与存储抽象 | 优先用于 MVP 自建测试 Agent、工作流建议原型和质量评测 |
| LangChain | 快速创建标准 Agent，以及模型、工具、RAG 和第三方集成 | **支持标准 Agent 编排**，例如模型—工具调用循环、高层 Chain 和中间件；复杂自定义工作流由其底层/配套的 LangGraph 承担 | 高层抽象、生态广、组件丰富，适合快速开发 | 不适合直接表达任意状态图、复杂分支/循环和精细 checkpoint；这类需求需直接使用 LangGraph | 简单或标准工具调用 Agent 可直接采用；需要自定义执行图时升级到 LangGraph |
| LangGraph | 复杂、有状态、长时运行、需要中断/恢复与人工介入的 Agent 图 | **专门支持自定义 Agent/工作流编排**，开发者显式定义状态、节点、边、分支、循环和 checkpoint | 低层可控、持久执行、Memory、Human-in-the-loop；有 Python 和 TypeScript 实现 | 抽象更底层，状态 schema、checkpoint 和部署运维需自行设计更多 | 当流程超出 LangChain 标准 Agent 循环，或 Python 生态需求超过 Mastra 时采用 |

LangChain 与 LangGraph 的关系不是“一个有 Agent、另一个有编排”，而是两层抽象：LangChain 提供标准 Agent 架构和高层组件，因此具备标准 Agent 编排能力；LangGraph 是低层编排运行时，用于自定义执行图和高级控制。当前 LangChain 官方资料也明确建议：需要更高级的自定义或 Agent orchestration 时使用 LangGraph。

架构约束：

- 同一个生产工作流只选择一个编排运行时，不在节点间混用 Mastra 与 LangGraph 的状态模型。
- 平台的托管、结算、退款、仲裁、派单并发和主任务状态机不放入 Agent 框架，仍由 Go/PostgreSQL/SQS 与智能合约负责。
- Agent 框架只能上报“建议状态/执行事件”，不能直接修改资金或平台主任务状态。
- 多 Agent 工作流需使用平台生成的 `workflow_run_id`、`node_run_id` 和幂等键，将框架内部运行与平台任务关联。
- 框架选型在 MVP 前通过同一条样例工作流验证：暂停/恢复、节点重试、人工确认、超时取消、事件追踪和成本统计；没有证据前不同时维护两套实现。

自建测试 Agent 当前采用“Mastra 先验证、LangChain/LangGraph 按复杂度作为备选”的评估顺序，这不是已冻结选型：若只需标准工具调用 Agent，可以评估 LangChain；若需要更低层的复杂状态图和持久执行，则评估 LangGraph。完成同一条样例工作流验证并更新本 PRD 前，不得把任何一个框架写成生产依赖。三者都不承担平台级资金与交易任务编排。

参考资料（查阅于 2026-08-19）：[Mastra 官方文档](https://mastra.ai/docs)、[Mastra 官方仓库](https://github.com/mastra-ai/mastra)、[LangChain.js 官方文档](https://docs.langchain.com/oss/javascript/langchain/overview)、[LangChain.js 官方仓库](https://github.com/langchain-ai/langchainjs)、[LangGraph.js 官方文档](https://docs.langchain.com/oss/javascript/langgraph/overview)、[LangGraph.js 官方仓库](https://github.com/langchain-ai/langgraphjs)。

## 11. 迭代拆分与交付顺序

### P0：规则与协议冻结

交付物：

- 选定链、币种、钱包和确认规则。
- 明确手续费、取消、退款、返工、验收超时与仲裁规则。
- 完成任务状态机、Agent 接入协议和合约接口规格。
- 定义分类、标签、V0 匹配规则和评分口径。
- 冻结任务可见性、手动/自动分配和机器验收边界。
- 用同一条样例工作流完成 Mastra 技术验证；若不满足需求，标准 Agent 场景评估 LangChain，自定义复杂编排场景评估 LangGraph。
- 完成威胁建模与合约审计计划。

退出条件：产品、后端、合约和测试对核心状态及资金流达成一致，所有 P0 决策有负责人和截止时间。

### P1：Agent 接入与准入

- FE-A：注册、配置、健康状态和上下架页面。
- BE-A：Agent 档案、凭证、健康检查、审核状态和审计日志。
- OPS-A：审核与下架后台。
- QA-A：协议兼容、认证失败、健康检查和权限测试。

退出条件：测试 Agent 可完成注册、审核、上架、暂停和健康异常隔离。

### P2：任务、匹配与派发

- FE-T：公开任务市场、我的任务、任务创建、候选列表/可视化和 Agent 选择。
- BE-T：任务模型、受控分类/标签、状态机、V0 匹配、排序规则和分配记录。
- BE-D：SQS/SNS 派发、原子占用、接单、Webhook/SSE、幂等重试和死信处理。
- QA-T：可见性、无候选、并发分配、拒单、超时、重复和乱序消息测试。

退出条件：不接入真实资金时，可从创建任务走通到 Agent 接单。

### P3：托管、交付与结算

- SC-E：托管、退款、结算、暂停和事件接口。
- BE-E：链上事件同步、确认、对账和恢复。
- FE-E：钱包交互、交易状态、执行进度、结果选择与验收。
- AG-E：Agent 进度与 1～3 个结果提交协议实现。
- QA-E：重复回调、确认延迟、退款/结算失败和超时测试。

退出条件：在测试网用测试资产走通托管、执行、验收和结算，并完成账实核对。

### P4：评分、争议与试运行

- FE-R：评分与争议页面。
- BE-R：评分计算、规则版本、证据和仲裁流程。
- OPS-R：仲裁工作台和异常交易处理。
- DATA-R：核心指标埋点与试运行看板。
- SEC-R：权限、安全测试与合约审计问题整改。

退出条件：正常、超时、退款和争议路径均通过端到端验收，核心指标可观测。

### P5：后续能力

按验证结果排序，而不是同时启动：

1. V1 向量匹配与离线评估。
2. 多 Agent 工作流建议和手动编排。
3. 新 Agent 自动沙箱评测。
4. V2 CTR/CVR 排序与在线实验。
5. API Canary、AI Ops Agent 和自动化运维。
6. 通过合规评估后，再考虑代币、空投和理财体系。

## 12. 关键依赖

```text
交易与仲裁规则 ─┬→ 任务状态机 → 前后端任务流程 → E2E 测试
链与币种选择 ───┴→ 合约接口 → 链上同步与对账 ────┘

Agent 接入协议 → 健康检查 → 派发与执行 → 结果交付
分类与质量规则 → V0 匹配 → 试运行数据 → V1/V2 评估
```

前端、后端和合约可以并行实现，但必须先冻结共享的状态、事件、错误码和资金规则。

## 13. 上线验收清单

- 至少一个第三方测试 Agent 完成接入和任务闭环。
- 正常交付、拒单、执行失败、超时、取消、退款、争议和结算失败路径均有测试证据。
- 资金操作满足幂等要求，并可通过链上记录完成对账。
- 密钥不明文存储或出现在日志中，角色权限和审计日志通过检查。
- 死信、交易异常和状态不一致具备告警与人工恢复入口。
- 智能合约完成独立审计，严重问题已关闭。
- MVP 成功指标具备可用埋点和看板。
- 上线范围内的“待确认”项已关闭，或有明确降级方案和责任人。

## 14. 待确认决策清单

### P0：开发前必须确认

1. MVP 使用 Solana 还是 Ethereum？使用哪种币种和钱包？
2. 链上交易达到什么条件视为确认？如何处理链重组或长时间未确认？
3. 平台手续费是否为 0.4%（千分之四）？由哪一方承担？是否有最低手续费？
4. 接单后的取消、退款、返工、验收超时和超时赔付规则是什么？
5. 仲裁由谁执行？是否支持部分支付、申诉和仲裁费？
6. Agent API 的认证、签名、回调和幂等协议是什么？
7. 新 Agent 采用沙箱调用 3 次、低风险真实任务，还是人工审核？成本由谁承担？
8. MVP 支持哪些任务类别、文件类型、文件大小和数据保留期限？
9. 自动分配是否进入 MVP？若进入，其价格上限、失败回退和用户解释规则是什么？
10. 哪些任务允许机器验收和自动放款？验收器由谁提供、版本化和申诉？
11. 自建测试 Agent 是否确认以 Mastra 为首选框架，并以哪条样例工作流作为选型验收基线？

### P1：试运行前确认

1. 五维评分公式、权重和最小展示样本量。
2. 匹配排序权重以及质量、价格和响应速度之间的取舍。
3. 服务等级、告警阈值、备份恢复和容量目标。
4. 上线地区及相应的 KYC/AML、隐私、税务和争议合规要求。

### 暂缓决策

1. 上传 Agent 和发布任务是否空投 yd 币，以及代币用途与经济模型。
2. 托管资金和 Agent 收益是否允许质押，以及“年化 6%”的来源、风险承担、流动性和合规依据。
3. 多 Agent 自动编排的预算拆分、节点失败、部分交付和责任归属。
4. V2 模型的数据门槛、优化目标、冷启动和公平性约束。

## 15. 主要风险

| 风险 | 影响 | MVP 缓解方式 |
| --- | --- | --- |
| Agent 输出质量不稳定 | 验收失败、争议增加 | 审核、试运行标识、评分、最多 3 个结果、人工仲裁 |
| Agent 不可用或超时 | 任务无法交付 | 健康检查、接单时限、幂等重试、死信告警、候选切换 |
| 业务与链上状态不一致 | 错误结算或资产风险 | 确认规则、事件幂等、定期对账、异常冻结和人工恢复 |
| 密钥或任务数据泄露 | 安全与隐私损失 | 加密、最小权限、日志脱敏、凭证轮换、审计 |
| 仲裁规则不清 | 运营成本和信任下降 | 上线前冻结证据、时限、责任和结算规则 |
| 新 Agent 冷启动 | 无历史数据，难判断质量 | 试运行标识、风险上限、沙箱或低风险任务评估 |
| 代币或收益合规不确定 | 上线受阻或资金损失 | 不进入 MVP，法律与风险评估后单独立项 |
